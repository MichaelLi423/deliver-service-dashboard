# ADR-0001：Windows 桌面 + Electron/React/TypeScript + 本地 SQLite

- **状态**：已接受（客户确认，2026-08-06；访问边界 2026-08-07 修订；实现细节 2026-08-07 在 tasks 0.2 选定；访问边界 2026-08-10 客户最终反馈再次修订为无应用内访问门槛）
- **日期**：2026-08-06（2026-08-07 修订访问边界与实现细节；2026-08-10 修订为无应用内访问门槛）
- **关联**：TBD-16 已解决；新增能力 `local-data-persistence`、`workbench-access`；需求规格第 12 章《运行与持久化边界》；tasks 0.2 实现细节决策

## 背景

搬迁服务工作台首版为搬迁负责人个人使用的业务记录与统计工具。此前技术栈、数据库、部署与认证形态均未确定（TBD-16 的一部分）。客户确认首版边界：仅个人使用、仅 Windows、桌面应用、本地数据、不接任何远程系统，并明确了备份恢复要求。2026-08-07 客户明确访问边界：首版个人使用，但提供**单一本地应用账号**作为应用访问门槛（首次启动初始化、后续登录、忘记密码恢复码重置；无多账号、注册、角色与权限管理，无远程认证、外部身份源与账号同步；账号仅为访问门槛、不加密 SQLite，Windows 操作系统账户仍是本机数据文件与备份的主要保护边界）。客户最终反馈（2026-08-10）进一步确认：个人单机使用、**无应用内访问门槛**——启动直接进入工作台，无应用内初始化、密码登录、恢复码、多账号/角色；内部唯一"本地用户"仅用于事实归属与用户名快照（actor snapshot），不是访问门槛；SQLite 不加密，Windows 操作系统账户仍是本机数据文件与备份的主要保护边界。本决定取代此前"无应用内登录、依赖 Windows 操作系统当前用户账户"与"单一本地账号登录门槛"的表述。

## 决定

1. 首版为 **Windows 桌面应用**，采用 **Electron + React + TypeScript**。
2. 全部业务数据持久化在**本机 SQLite** 数据库中，不接远程数据库、云同步或外部业务系统。
3. 应用为**个人单机使用、无应用内访问门槛**：启动直接进入工作台，不提供应用内初始化、密码登录、恢复码或账号切换；不支持多账号、注册、自助新增用户、角色与权限管理；无远程认证、外部身份源或账号同步。内部唯一"本地用户"仅用于事实归属与用户名快照，不是访问门槛；本地 SQLite **不加密**；Windows 操作系统账户仍是本机数据文件与备份的**主要保护边界**，内部本地用户不能防止直接读取数据库文件。
4. 手工录入事实与工作量责任人归属内部唯一"本地用户"，动作记录持久化用户内部 ID 与当时用户名快照；历史统计不因以后用户名修改而动态变化。本规则不因仅有一个用户而省略。历史数据导入等受保护操作仅对受信工作台窗口开放（trusted renderer/IPC 守卫），迁移运行审计记录本地用户 ID 与确认时用户名快照。
5. 数据保护采用**本地备份**：每日首次使用时自动备份并仅保留最近 7 份；支持立即手动备份到所选本地目录，以及从所选本地备份恢复（恢复前确认并验证可读，失败不覆盖当前数据）。

本决定确认架构方向与实现细节：Electron 43.3.0、Forge 7.11.2 + webpack-typescript + React、SQLite 访问采用 Node 内置 node:sqlite、schema 迁移采用 PRAGMA user_version、数据目录为 userData/data、备份采用在线 backup + integrity_check + 原子恢复并可做恢复前安全快照、连接启用 WAL/foreign_keys/busy timeout、金额以分整数物理表示、业务时间仅记录业务日期（yyyy-mm-dd）而审计/技术时间保留精确 ISO（tasks 0.2 决策，时间口径见 openspec design D30）。

## 原因

- 单机、单用户、单 Windows 桌面的规模下，本地 SQLite 提供事务性单文件持久化，运维与备份最简单，且不引入网络依赖。
- 个人单机使用下无应用内访问门槛最符合使用预期：启动即用、无密码与恢复码维护成本；同时保留内部唯一"本地用户"作为手工录入事实、工作量与迁移审计的归属载体与用户名快照，使历史统计稳定、审计可追溯，不引入多用户、角色、权限或远程认证的复杂度。
- 本地 SQLite 不加密，本机数据文件与备份的保护由 Windows 操作系统账户承担，避免误称访问门槛可防止直接读取数据库文件。
- 本地备份是单机数据唯一的保护手段；每日自动备份 + 最近 7 份轮转在恢复窗口与磁盘占用间取得平衡，手动备份/恢复覆盖立即与重大变更场景。

## 后果

**正面**：首版范围封闭可控，无远程基础设施、无多用户/角色/权限模型、无云同步维护成本；无应用内访问门槛使个人单机使用即开即用，无密码/恢复码维护负担；内部唯一"本地用户"提供事实归属与用户名快照载体，迁移审计可追溯；数据可离线完整使用；备份/恢复路径明确。

**代价/风险**：

- **无多设备同步**：数据仅存在于单台 Windows 机器，换机或换环境需通过手动备份/恢复迁移，需在交付文档中说明。
- **无访问门槛即无应用内数据保护**：SQLite 不加密，直接读取数据库文件仍可能（Windows 操作系统账户为主要保护边界），须在交付文档中明确，不得声称本地用户可防止读取数据库文件。
- **需要 schema 迁移机制**：本地 SQLite 数据结构升级时必须迁移现有数据，迁移失败须保留可恢复状态。
- **需要备份恢复验证**：备份与恢复路径必须可测试、失败不静默，需纳入端到端验收。
- **需要 Windows 安装包**：须产出 Windows 安装与升级形态，首次安装由部署运维人员完成，并已在 Windows 目标环境验收。
- **原型生产重写**：`prototype/relocation-workbench/selected/relocation-workbench-selected.html` 仅为设计依据，生产实现须在 Electron/React/TypeScript 中重写，不复制原型技术代码。

## 明确不做

数据库文件/备份加密（无应用内访问门槛、SQLite 不加密，超出已确认边界）、应用内初始化/密码登录/恢复码、多账号与角色权限管理、远程认证与外部身份源、云备份/云同步（超出已确认边界，属后续变更而非本决定范围内）。
