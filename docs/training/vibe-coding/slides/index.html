04 / OPENSPEC

核心流程与验证边界

explore → propose → apply → archive

explore摸现状
propose出规格
apply按规格实现
archive完成后归档

/opsx-verify

项目已有启发式命令：读取 artifacts、搜索代码，判断完整性 / 正确性 / 连贯性。

无需 profile，不自动跑项目测试；历史阶段没有运行。

strict 只验结构

验证规格格式、requirement/scenario 结构与可解析性。

不证明 proposal/design/tasks 完成度，也不证明行为正确。

05 / 开发方法

先判断：目标已知，还是原因未知

TDD vs diagnosis

TDD · 已知目标行为

保存后应立即刷新

先写失败测试，再实现到变绿。

DIAGNOSIS · 未知故障原因

虚构案例：搜索框按 Enter 没反应，但点击按钮正常。

  1. 复现：Enter 失败 / 点击正常
  2. 最小化：只保留搜索表单与 keydown 路径
  3. 假设：焦点、preventDefault、缺少 submit 绑定
  4. 插桩：keydown 已触发，submit handler=0；排除焦点 / 后端
  5. 修复：统一走 form onSubmit
  6. 回归：Enter 与点击各触发一次查询

05 / 开发方法

做对了，靠什么确认

四层证据

01

strict

规格格式、requirement/scenario 结构与可解析性

不证明 artifacts 完成度或行为

02

规范映射
启发式核对

历史人工/等效规范映射；/opsx-verify 可辅助

历史阶段未运行该命令；只覆盖已写场景

03

机器执行证据

tests · 被断言行为
typecheck · 类型一致
build/package · 可构建打包
E2E · 特定环境与路径

不能外推到未断言行为或其他环境

04

code review

安全、清晰、可维护

评审不能穷尽所有行为

每一层回答不同问题，合起来才形成证据链。
