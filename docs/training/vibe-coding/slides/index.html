05 / 开发方法

两个入口，方向不同

TDD vs diagnosis

TDD · 已知目标行为

保存后应立即刷新

先写一个会失败的测试，再实现到变绿。项目案例完整演示。

DIAGNOSIS · 未知故障原因

虚构教学微案例：搜索框按 Enter 没反应，但点击按钮正常。

  1. 复现：Enter 失败 / 点击正常
  2. 最小化：只保留搜索表单与 keydown 路径
  3. 假设：焦点、preventDefault、缺少 submit 绑定
  4. 插桩 / 排除：keydown 已触发，submit handler=0；排除焦点 / 后端
  5. 修复：统一走 form onSubmit
  6. 回归：Enter 与点击各触发一次查询

独立于项目四阶段，不混同历史 preset-failure，不声称来自仓库真实缺陷。

26
05 / 开发方法

做对了，靠什么确认

四层证据

01
strict
规格格式、requirement/scenario 结构与可解析性
不证明 artifacts 完成度或行为
02
规范映射 / 启发式核对
历史人工/等效规范映射；/opsx-verify 可辅助
历史阶段未运行该命令；不覆盖场景外
03
机器执行证据
tests：被断言行为
typecheck：类型一致
build/package：可构建打包
E2E：特定环境与路径
不证明未断言行为、其他环境或代码质量
04
code review
安全、清晰、可维护
不穷尽所有行为

四层互补；机器结果不能读成“全部正确”。
