逐分钟讲稿，口播为正常中文。总时长 90 分钟、共 34 页：概念与安全 8、第一次 OpenCode 会话 12、三套工具教程 22、开发方法 12、项目演示 22、日常落地 6、Q&A 8。演示机械细节见 [demo-runbook.md](./demo-runbook.md)，逐页讲解卡见 [presenter-preparation.md](./presenter-preparation.md)。

## 第 1 段：概念与安全（0–8 分钟，页 1–5）

**0:00–1:00 页 1 封面**

> 大家好，欢迎参加《Vibe Coding》。副标题是"从需求到证据的受控开发闭环"。90 分钟：8 分钟概念，12 分钟看一次真实的 OpenCode 会话，22 分钟讲三套关键工具，12 分钟讲开发方法和证据，22 分钟走一个完整项目演示，6 分钟日常落地，最后 8 分钟问答。不跟做，没有考核。

**1:00–2:30 页 2 学完能做什么**

> 学完这门课，你能做到三件事：第一，判断一个任务该让 AI 做多少、自己必须守住什么；第二，会开一个受控的编码会话，看懂它的状态、计划、权限、diff 和撤销；第三，能用 TDD、诊断、规范核对和代码评审四层证据确认"做对了"。有一点先讲清楚：现场不调用 Agent，所有 Agent 输出都是连续编号的静态重构材料回放——这些材料依据已核验的会话步骤和历史输出摘要重新排版，不是原始界面截图，也不是现场 Agent 输出，保证可复现。

**2:30–4:30 页 3 模型/Agent/tool/session**

> 先分清四个词。模型是推理引擎；Agent 是围绕模型组织起来的执行主体，会调用工具；工具是 Agent 能用的编辑器、终端、搜索这类能力；session 是一次会话——它有工作目录、上下文和权限边界。这门课的操作单元是会话。记住：会话里发生的一切，都有状态可以检查。

**4:30–6:30 页 4 受控开发**

> 校准一个词。Vibe Coding 在外面的说法很玄，好像写代码靠"感觉"。本课的口径是"受控 AI 辅助开发"：人定义目标、约束、决策和验收证据，AI 负责辅助分析和实现。人始终握着方向盘。证据是判断"做对了没有"的唯一依据。

**6:30–8:00 页 5 安全红线**

> 60 秒讲一条红线，演示和课后都适用。第一，不上传敏感信息；第二，不展示密钥；第三，AI 没有任何生产权限；第四，破坏性操作、数据操作、依赖变更、合并或发布，都要人工确认。这四点会贯穿后面所有演示。

## 第 2 段：第一次 OpenCode 会话（8–20 分钟，页 6–11）

> 开场（8:00–8:20）：这段以连续编号的静态重构材料呈现。四份材料对应四个步骤，每步解释"当时发生了什么、为什么"。材料依据已核验的会话步骤和历史输出摘要重新排版，不是原始界面截图、不是现场 Agent 输出。真实因果，不是演示视频。

**8:00–10:00 页 6 开始前：仓库与 Git**

> 开始前先做两件事：确认仓库干净，确认你在哪个分支。这决定会话的起点可信。我们用 `git status` 和当前分支作为证据，不靠记忆。这也是一条日常习惯：任何 AI 参与的工作，先有一个干净、可回退的起点。

**10:00–12:00 页 7 OpenCode 是什么**

> OpenCode 是一个跑在终端里的 AI 编码工具，官网 opencode.ai。它的价值不在"更快打字"，在于把模型、工具和权限组织成一次可检查的会话。主界面分三个区：对话、文件差异、终端。我们接下来四个步骤都在它里面发生。

**12:00–14:00 页 8 步骤 1：启动与状态**

> 第一步，启动会话。会话建立后先看状态：当前模型是什么、在哪个工作目录、有哪些可用工具。这一步不是走过场——状态就是会话的"边界说明书"，看清了才知道 AI 能做什么、不能做什么。

**14:00–16:00 页 9 步骤 2：只读理解**

> 第二步，只读理解。让 Agent 先读仓库，回答"这是什么项目、目录怎么组织、构建怎么跑"，但明确不许改文件。这一步的价值是验证理解：如果它连项目都读不对，后面一切免谈。读得对，再谈改。

**16:00–18:00 页 10 步骤 3：权限**

> 第三步，模式与权限。OpenCode 的权限有三个值：allow、ask、deny。默认多数操作是 allow，直接放行；只有命中 ask 的操作才弹出请求、需要你批准；deny 直接拒绝。这次回放**显式切到 Plan 模式**，并把相关操作的 permission 配置为 ask——Plan 默认对编辑和 bash 类操作设 ask，所以你会看到批准请求出现。权限不是麻烦，是人握着方向盘的具象化。

**18:00–20:00 页 11 步骤 4：diff/undo/验证**

> 第四步，改动之后的三个动作：看 diff——确认改动范围没有夹带私货；undo——`/undo` 单次撤销上一条用户消息及其后的回复与文件改动，可连续执行 `/undo` 继续向前，`/redo` 恢复；跨会话回退或需要明确版本点时依赖 Git；验证——跑测试、类型检查或构建，用结果说话。记住这个顺序：diff 是人工把关，undo 是单步安全网，验证是证据。

## 第 3 段：三套关键工具（20–42 分钟，页 12–25）

**20:00–21:00 页 12 工具选择地图**

> 工具很多，先看地图。我们要讲三套：skills 技能包（工作流标准化）、oh-my-opencode-slim（多 Agent 编排）、OpenSpec（规范与验收）。MCP 这张地图上也出现：本页给它 1 分钟做定位，页 25 再给 1 分钟讲边界。它是连接外部系统的开放协议，只有当内置工具不够、需要接外部系统时才用；本项目没有 MCP 配置，演示不涉及。一句话：先用内置，不够再谈协议。

**21:00–22:00 页 13 skills：标准 vs 技能包**

> skills 有个"标准 vs 技能包"的区分。背景是 Agent Skills 开放标准，以及 skills.sh / Vercel Labs 这个生态——它们定义技能怎么写、怎么分发。而 mattpocock/skills 是一个具体的人维护的技能包。别把"某个技能包"当成"官方标准"。

**22:00–23:30 页 14 mattpocock/skills 是什么、为什么**

> mattpocock/skills 是 Matt Pocock 维护的个人技能集合。为什么值得看？它把几类高频工作流做成了可复用的技能：grill-with-docs（用文档带路澄清需求）、tdd（测试先行）、diagnosing-bugs（按证据诊断）、code-review（代码评审）。对我们来说，它就是"受控开发"的现成工作流模板，不是官方标准。

**23:30–25:30 页 15 安装与审阅**

> 怎么用？安装示例：`npx skills@latest add mattpocock/skills`。三个要点：第一，先审阅再启用——技能包会往你的工作区写文件，先看它加了什么；第二，上游要求安装时选择 `setup-matt-pocock-skills`，并在每个仓库运行一次 `/setup-matt-pocock-skills`；第三，插件安装与 skills.sh 安装二选一，避免同一技能重复注册。具体版本以官网和上游为准，命令只讲解不现场执行。

**25:30–27:00 页 16 grill/tdd/diagnose/code-review 用法**

> 四个重点技能怎么落地？grill-with-docs：需求澄清时先读文档、再连环提问，把歧义逼成可验证的约束。tdd：先写会失败的测试。diagnosing-bugs：先收集日志、复现步骤、最小环境，再动代码。code-review：对照安全、清晰、可维护三个视角。这四个技能分别对应闭环的四个环节。

**27:00–29:00 页 17 何时单 Agent**

> 什么时候一个 Agent 就够？任务边界清晰、串行依赖、你一个人就能描述清楚时，单 Agent 最简单、最容易回看。什么时候需要更多？任务可以切成独立子问题、需要并行或对抗性检查时，才考虑编排。原则：能单 Agent 就不编排——编排引入协调成本。

**29:00–31:00 页 18 oh-my-opencode-slim 是什么、为什么**

> oh-my-opencode-slim 是给 OpenCode 加多 Agent 编排能力的第三方插件，注意：社区插件，不是 OpenCode 官方。为什么存在？单 Agent 的长任务会上下文膨胀、注意力漂移；多 Agent 把任务分给不同职责的 Agent，各干各的，再汇总。抽象阶段可以理解为"计划 → 实现 → 复核"，但那是阶段不是角色；插件真实内置角色是 Orchestrator、Explorer、Oracle、Council、Librarian、Designer、Fixer，Observer 可选。适合复杂任务，不适合小改动。

**31:00–33:00 页 19 安装/配置/权限**

> 安装示例：`npx oh-my-opencode-slim@latest install`，然后登录、刷新，`ping all agents` 检查各角色就绪。三个必须讲的边界：配置路径（默认用户级配置 `~/.config/opencode/oh-my-opencode-slim.json(c)`，项目级 `.opencode/oh-my-opencode-slim.json` 只是可选的覆盖——不要笼统说"统一写进项目配置"）；权限（安装和运行会读写配置、调用模型，看清它请求什么再批准；安装不会创建 agent 目录）；成本（Council 这类多模型投票角色会明显增加 token 消耗）。两个环境变量：后台编排依赖 `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true`，整体禁用 `OH_MY_OPENCODE_SLIM_DISABLE=1`——不用时关掉。高级命令放手册，不放主课件。

**33:00–35:00 页 20 agents 分工与最小用法**

> 最小用法：Orchestrator 分派任务，Explorer 只读侦察，Fixer 有界实现，Oracle 按需做高风险评审；Designer 处理 UI，Librarian 查官方资料；Council 多模型投票，按需开启且成本高。不要一上来把所有角色都开。判断标准还是风险适配：改动小、风险低，单 Agent 就够；跨模块、需要独立复核，再上编排。演示里我们其实主要用单 Agent 流程，编排只做概念定位。

**35:00–36:30 页 21 OpenSpec 是什么、为什么**

> OpenSpec 是规范优先的工作流工具，官网 openspec.dev。为什么用？它把需求变成规格、把规格变成可验证场景，实现后再逐条核对。它解决一个具体问题：AI 写了代码之后，凭什么说它符合需求？答案是证据，而 OpenSpec 就是证据的组织方式。

**36:30–38:00 页 22 目录与 artifacts**

> 一个 change 的产物有哪些？proposal（提案）、spec（规格，SHALL + 场景）、design（设计决策）、tasks（最小步骤）。目录有约定：changes 里放进行中的，归档后进 archive。演示用的培训夹具放在 docs 下，不污染正式扫描。artifact 是文档，不是代码——这层要分清。

**38:00–39:30 页 23 CLI vs 聊天命令**

> OpenSpec 有两种用法：终端 CLI，和聊天命令。注意，命令形态会随宿主工具不同而变化，本课只展示本仓库实际命令：`.opencode/commands/` 里已有的连字符形式 `/opsx-propose`、`/opsx-apply`、`/opsx-verify`、`/opsx-archive`、`/opsx-explore`。聊天命令是给会话用的——Agent 在会话里用它走流程；CLI 是给人手动操作的。这是项目已有资产，不是本课安装的。

**39:30–41:00 页 24 propose → apply → verify → archive**

> 核心流程四步：explore 摸清现状；propose 生成提案和规格；apply 按规格实现；archive 完成后归档。verify 单独说：本仓库 `.opencode/commands/opsx-verify.md` 是项目已有的启发式命令——读取 artifacts、搜索代码，做完整性/正确性/连贯性的启发式判断；它不需要什么 profile 前置，也不会自动跑项目测试。但本课不声称 green-final 阶段真实运行过这条命令。最后强调：strict 只验证规格结构，不验证行为——这句后面还会重复。

**41:00–42:00 页 25 MCP 边界**

> MCP 收个尾。它是协议，不是运行时；它解决"AI 怎么连外部系统"的问题。判断标准只有一条：内置工具不够、必须接外部系统时再用。本项目没有配置，所以本课不演示。别为用它而用它。

## 第 4 段：开发方法（42–54 分钟，页 26–27）

**42:00–48:00 页 26 TDD vs diagnosis**

> 两个入口，别混。TDD：目标行为已知——"保存后应该立即刷新"——那就先写一个会失败的测试，把期望钉死，再实现到变绿；这一条在项目案例里完整演示。diagnosis：故障原因未知，用一个**明确标注虚构**的静态教学微案例——"搜索框按 Enter 没反应，但点击按钮正常"——走六步证据链：**复现**（Enter 失败、点击正常）→ **最小化**（只保留搜索表单与 keydown 路径）→ **假设**（焦点问题、preventDefault、缺少 submit 绑定）→ **插桩/排除**（keydown 已触发，但 submit handler 调用数为 0，排除焦点与后端）→ **修复**（统一走 form onSubmit）→ **回归测试**（Enter 与点击均触发一次查询）。这个微案例独立于项目四阶段历史证据，也不同于历史 preset-failure；它是教学重构示例，不声称来自仓库真实缺陷。TDD 是从需求出发写证据，diagnosis 是从故障出发找证据。方向不同，工具不同，但都靠证据。

**48:00–54:00 页 27 四层证据**

> "做对了"这件事要四层证据叠起来。第一层，OpenSpec strict：只验 CLI 校验到的规格格式、requirement/scenario 结构与可解析性，不证明 proposal/design/tasks 完成度，通过也不等于行为对。第二层，规范映射/启发式核对：把实现和 spec 场景逐条对照——本课展示的是**历史人工/等效规范映射**；项目里 `/opsx-verify` 可以辅助这类核对，但本课不声称当时运行过它。第三层，机器执行证据，每一项都有明确边界：tests 只证明被断言的特定行为；typecheck 只证明类型一致性；build/package 只证明可构建、可打包；E2E 只证明特定环境、特定路径的特定行为。第四层，code review：人看安全、清晰、可维护。四层互补，谁也替代不了谁。一会儿演示里你会看到每一层长什么样。

## 第 5 段：项目整合演示（54–76 分钟，页 28–32）

> 开场（54:00–54:30）：演示需求来自本项目——提醒面板配置"临期窗口"。范围小、有真实歧义、可观察验证、脱敏数据。全程静态回放。

**54:00–56:00 页 28 原始需求**

> 原始需求一句话：在提醒面板里让负责人配置"临期窗口"。背景：搬迁服务里每个项目有手工维护的提醒，按日期分临期、今日到期、已逾期；临期窗口就是"多少天以内算临期"。就这么一句话，看起来清楚，其实藏着好几个歧义。

**56:00–60:00 页 29 grill 澄清**

> 我们用 grill-with-docs 澄清，三个问题收敛出边界。第一个问题：0 合法吗？合法——窗口为 0 表示未来提醒都不标临期，今日到期和已逾期不受影响。第二个：能填多大？只接受 0 到 9007199254740991 的非负安全整数，超范围拒绝；"无额外业务上限"不等于任意大整数。第三个：什么时候生效、用户怎么确认？显式保存前不生效，保存后立即刷新并持久化，提醒行显示日期。看，一句话的需求，澄清出五条可验证的约束。

**60:00–64:00 页 30 专用 training change/spec**

> 这里必须讲一段历史，防止误导。演示依托的原 `add-relocation-service-workbench` change 已经归档，不再是进行中。当前正式 spec 还是旧版，没有这些训练边界。所以课程用 `docs/training/vibe-coding/training-change/` 这个专用培训夹具冻结当时的叙事——它不是产品 change，OpenSpec CLI 不扫描它，也没有任何批准语义。四阶段 commit 只是历史训练分支上的证据快照。规格里写的是约定行为和验收场景，不是实现步骤。

**64:00–70:00 页 31 Red 与 preset-failure**

> 先看 Red：red-test 快照上，先写的失败测试红了——domain+integration 32 个通过，main 新增 2 项以 V2_MUTATION_UNKNOWN 失败，renderer 新增 1 项因找不到"临期窗口"控件失败。红是"行为已经写明、实现还没跟上"的证据。再看 preset-failure：IPC、facade、UI 全接通，界面能点，但实现错误地要求窗口必须不小于 1——只有 0 的用例失败，负数和非整数反而通过。表面可用，行为错了。这就是预设失败的教材意义。

**70:00–76:00 页 32 Green / review / verify**

> 最后看 Green 和两层质量门。green-final 快照上：4 个聚焦文件 95 tests 通过，全量 93 files/1076 tests 通过。规范核对：strict 的"Change is valid"是 2026-08-10 的历史输出——原 change 已归档，当前 HEAD 不能重跑这条命令，现场只展示由历史输出摘要重构的静态材料；spec 场景与证据的逐条对照是**历史人工/等效规范映射**的静态重构材料，当时没有运行 `/opsx-verify`，现场不声称运行过。代码评审：历史上真实发现过两个 medium（超安全整数静默改值、renderer 未证明立即刷新）和两个既有 low（IPC 参数袋、外部渠道否定测试），修正后无 blocker；透明说明：最后三项最小修正之后没有再执行第三轮独立 Oracle 评审，今天的终审是课程内容终审，不是代码分支的新一轮评审。UI 上最后确认：填 0 保存，未来提醒退出临期，today/overdue 不变，提醒行有日期。证据链闭环。再次强调：这些证据来自 macOS arm64 开发机，不代表 Windows；也不代表产品批准——它只是培训夹具的历史证据。

## 第 6 段：日常落地/风险适配（76–82 分钟，页 33）

> 回到日常，六个检查点收束：先文档后提问；规范写约定和证据；TDD 先红；diff 把关再绿；review 看质量；verify 对约定。强度按风险适配：低风险用简短任务约定和聚焦验证，中高风险加深文档、测试和 review 深度。但目标、边界、验证证据这三样，任何强度都不能省。跨 shared IPC/main/renderer 这类技术路径，即使业务影响小，集成风险也按中等处理。
