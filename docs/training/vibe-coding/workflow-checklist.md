# 工作流检查清单（workflow-checklist）

本清单配合 90 分钟、26 页课程使用，汇总开发闭环的两个入口（TDD vs diagnosis）、四层证据、六个最佳实践检查点与风险分级。配合 [CONTEXT.md](./CONTEXT.md) 词汇表使用。

## 开发闭环

需求澄清 → 规范 → 实现与验证 → 代码评审/规范核对

任一步骤发现偏差即返回上一步修正，直到满足验收证据。闭环里有两个入口，别混：

### TDD 入口：已知目标行为

- 适用：你知道"做对了是什么样"——例如"保存后应立即刷新并持久化"。
- 第一步：**先写一个会失败的测试**，把期望行为钉死（Red）；再实现到测试转绿（Green）。
- 红的含义：行为已经写明、实现还没跟上——这是预期证据，不是故障。

### diagnosis 入口：未知故障原因

- 适用：你只知道"出问题了"，不知道原因。页 21 用一条**明确标注虚构**的教学微案例演示："搜索框按 Enter 没反应，但点击按钮正常"。
- 第一步：**先收集证据**——复现、最小化、假设、插桩/排除，定位之后再改代码。
- 完整链条（虚构微案例的具体观察与修复，独立于项目四阶段历史证据，不混同历史 preset-failure，不声称来自仓库真实缺陷）：
  1. **复现**：Enter 失败、点击按钮正常；
  2. **最小化**：只保留搜索表单与 keydown 路径；
  3. **假设**：焦点问题、preventDefault、缺少 submit 绑定；
  4. **插桩/排除**：keydown 已触发，但 submit handler 调用数为 0，排除焦点与后端；
  5. **修复**：统一走 form onSubmit；
  6. **回归测试**：Enter 与点击均触发一次查询。
- 铁律：证据不足不猜测；一次只改一个变量，改完用同一证据重新验证。

两个入口方向不同、第一步不同，但都靠证据收束。本课 TDD 在项目案例演示；diagnosis 用页 21 这条虚构微案例演示——微案例独立于项目四阶段历史证据，四阶段并未真实执行完整 diagnosis，不冒充。

## 四层证据（review/verify 的完整含义）

"做对了"要四层证据叠加，任何一层单独都不够：

| 层 | 是什么 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| 1. OpenSpec strict | `validate --strict` 的"Change is valid" | CLI 校验到的规格格式、requirement/scenario 结构与可解析性 | 行为符合性、proposal/design/tasks 完成度 |
| 2. 规范映射/启发式核对 | 历史人工/等效规范映射（本课展示；项目里 `/opsx-verify` 可辅助这类核对，但本课不声称当时运行过它） | spec 场景与实现的逐条对照 | 场景之外的隐含行为 |
| 3. 机器执行证据 | 测试、typecheck、build/package、E2E 的真实输出 | tests 只证明被断言的特定行为；typecheck 证明类型一致性；build/package 证明可构建可打包；E2E 证明特定环境特定路径 | 未断言行为、其他环境、代码质量 |
| 4. code review | 人对照安全、清晰、可维护检查 | 质量与债务 | 穷尽所有行为 |

第 1 层只是门槛，第 4 层不能机器替代，第 2、3 层是主体证据。第 1 层在本课为 2026-08-10 历史输出：原 change 已归档，当前 HEAD 不能重跑 strict；training-change 是静态夹具不被 CLI 扫描，只能人工阅读。

## 六个检查点

1. **需求澄清（grill-with-docs，见 mattpocock/skills 技能包）**：先读文档再提问；目标、边界、验收证据三者明确再动手；歧义落到可观察验证的陈述。
2. **规范（propose / spec）**：只写约定行为与证据，不写实现步骤；不新建与归档机制冲突的重叠 change（课程演示用 [training-change/](./training-change/README.md) 夹具，不污染 CLI 扫描）。
3. **TDD Red**：先写会失败的测试；确认测试确实表达验收证据；红是预期证据。
4. **实现与 Green（apply diff + 测试通过）**：在规范约束下实现；看 diff 确认范围；红转绿作为可见信号。
5. **代码评审**：关注安全、清晰、可维护；预设失败演示靠测试与规范核对抓行为偏差、靠评审补质量视角。
6. **规范核对（verify）**：实现与 spec 逐条对照；评审与核对互补（质量双门），不可互相替代。

## 风险分级

流程强度按风险适配调整，但**目标、边界、验证证据在任何等级下都不可省略**；六个控制意图全部保留，不因风险低而省略检查点。

| 风险等级 | 判定特征 | 流程强度 |
| --- | --- | --- |
| 高 | 涉及公共 API、数据/安全影响、跨模块大改动、业务歧义大 | 六个控制意图全部完整执行；文档、测试与 review 深度最大 |
| 中 | 改动范围中等、影响局部、歧义可澄清 | 六个控制意图全部保留；提高文档、测试与 review 深度 |
| 低 | 范围小、可观察验证 | 六个控制意图全部保留；需求/规范压缩成简短任务约定，使用聚焦验证 |

**演示定位**：本课演示需求为"提醒面板内配置临期窗口"。作为培训夹具，产品合入风险低；但技术路径跨 shared IPC / main / renderer，集成风险按中等处理，保留完整聚焦证据路径（grill 任务约定 + Red/Green 聚焦测试 + strict/规范映射 + review）。
