# 工作流检查清单（workflow-checklist）

本清单汇总开发闭环的六个最佳实践检查点，并给出风险分级。配合 [CONTEXT.md](./CONTEXT.md) 词汇表使用。

## 开发闭环（本课只讲 TDD，不讲诊断）

需求澄清 → 规范 → TDD 的 Red/Green 实现与验证 → 代码评审/规范核对

任一步骤发现偏差即返回上一步修正，直到满足验收证据。

## 六个检查点

### 1. 需求澄清（grill-with-docs）

- 先读文档再提问，用文档带路，不凭空假设。
- 目标、边界、验收证据三者都明确后再动手。
- 歧义要落到"可观察验证"的陈述，而不是感觉。

### 2. 规范（OpenSpec propose / spec）

- 需求澄清的产出进入规范，形成可验证的验收场景。
- 规范只写约定行为与证据，不写实现步骤。
- 不创建与已有 change 重叠的变更：演示回放 `add-relocation-service-workbench` 进行中 change 的原始 propose 如何形成"临期窗口可配置"基础规则；本次 grill 发现的精细边界在同一个进行中 change 内更新 spec，不新建 change。

### 3. TDD Red

- 先写会失败的测试，作为"行为尚未实现"的证据。
- 确认测试确实表达验收证据，而非测试本身写错。
- 红是预期证据，不是故障。

### 4. 实现与 Green（apply diff + 测试通过）

- 在规范约束下实现，只做该做的事。
- 查看 diff，逐段对照规范确认改动范围。
- 测试由红转绿作为"满足验收证据"的可见信号。

### 5. 代码评审（code review）

- 关注安全、清晰、可维护。
- 预设失败演示：IPC/facade/UI 已接通、表面可操作，但实现错误拒绝 0（要求 >=1）；测试与规范核对抓住行为偏差，靠证据纠偏。

### 6. 规范核对（OpenSpec verify）

- 把实现与规范逐条对照，确认约定行为全部满足。
- 评审与核对互补（质量双门），不可互相替代。

## 风险分级

流程强度按风险适配调整，但**目标、边界、验证证据在任何等级下都不可省略**；六个控制意图全部保留，不因风险低而省略其中某些检查点。

| 风险等级 | 判定特征 | 流程强度 |
| --- | --- | --- |
| 高 | 涉及公共 API、数据/安全影响、跨模块大改动、业务歧义大 | 六个控制意图全部完整执行；需求与规范落成正式文档，测试全量，review 深度最大 |
| 中 | 改动范围中等、影响局部、歧义可澄清 | 六个控制意图全部保留；提高文档、测试与 review 深度，证据路径完整 |
| 低 | 演示/培训夹具、范围小、可观察验证 | 六个控制意图全部保留；需求/规范可压缩成简短任务约定，使用聚焦验证 |

**演示定位**：本课演示需求为"提醒面板内配置临期窗口"。作为培训夹具，产品合入风险低；但技术路径跨 shared IPC / main / renderer，集成风险按中等处理，保留完整且聚焦的证据路径（简短任务约定 + Red/Green 聚焦测试 + verify 规范核对）。
