## 2. 业务目标

1. 搬迁负责人通过工作台完成从进单、联系客户、安排运输公司与工程师、录入单据、记录执行状态到费用申请的全流程控制。
2. 工作台用于记录关键时间点信息、把控搬迁项目流程、回顾工作情况。
3. 工作台记录并统计各业务对象的工作量（开单、Ship-to 申请、损坏维修备件、二维码申请、序列号地址更新、掉票等），支撑季度汇报类统计报表。

## 3. 首版范围

### 3.1 范围内

1. 首版记录搬迁、认证、单寄备件、PM 四类开单业务及其工作量。
2. 只有搬迁业务建立搬迁项目，并进入完整的进单、执行、验收和掉票生命周期。
3. 首版仅由搬迁负责人使用并维护工作台数据；应用不提供应用内登录/账号体系，访问依赖 Windows 操作系统当前用户账户（见第 12 章）。
4. 涵盖进单与未进单先执行、开单、搬迁批次与物流、Ship-to 与序列号地址更新、损坏维修与备件、服务二维码与二维码申请、待办与提醒、掉票等子流程。
5. 提供进单金额、掉票金额与次数、开单量、损坏维修记录数量与备件金额及合同占比、物流费用、Ship-to 申请工作量、二维码申请工作量、序列号地址更新记录数等统计与报表。
6. 支持对现有 Excel 历史记录的存量数据一次性迁移；迁移由工作台外的部署运维人员执行，工作台不提供迁移与补录入口。

## 4. 角色与协作边界

1. 搬迁负责人是首版唯一的数据使用与维护角色（应用无应用内登录，依赖 Windows 操作系统当前用户账户访问本机数据，见第 12 章）；外部业务事实（经理批复、工程师执行、运输公司信息、合同金额等）由负责人录入或确认，系统自动记录或迁移导入的数据不视为手工录入。
2. 销售：无独立账号、审批入口或数据维护入口；首版不记录销售通知（已确认）。
3. 经理：对"未进单先执行"进行批复；批复信息（批复、原因、缺失项）由搬迁负责人手工记录，经理无独立审批入口。
4. 工程师：上门执行信息由搬迁负责人记录；工程师无独立账号或数据维护入口。
5. 运输公司/供应商：报价与费用信息由搬迁负责人维护；供应商无独立账号或数据维护入口。
6. 首版按单个搬迁负责人设计，不设项目负责人字段，不实现多人账号和数据权限控制；各项工作量指标的责任人取对应动作记录中的负责人，不依赖项目负责人字段或登录账号。

## 5. 领域对象与关系

术语定义以 CONTEXT.md《搬迁服务》为准，本节只描述对象间关系，不重复整个词汇表。

### 5.1 核心对象

- 合同：与搬迁项目一一对应的合同；一份合同只对应一个搬迁项目；记录合同开始日期与合同截止日期。
- 搬迁项目：与合同边界一致的整体服务范围，统一验收、统一核算；与合同共用 ECC；记录区域、旧址与新址联系人、默认旧址与新址、计划上门与计划运输时间、场地确认、实际装机完成时间等。
- ECC：一份合同及其唯一搬迁项目共用的全局唯一业务编号；正式进单后必填，未进单先执行阶段可暂用系统临时编号。
- 搬迁批次：同一搬迁项目内、同一次运输安排下的一组搬迁仪器；一个项目可有多个批次；记录运输公司、原价与折后价（人民币）、预算价格、成交价格与实际物流费用（人民币）及登记日期。
- 搬迁仪器：按序列号识别的一台仪器；记录仪器名称（必填）、型号（选填）、UPS 是/否、所属搬迁批次、"二维码是否申请"（手工是/否）及拆装进度。
- 上门活动：一次实际到访的现场工作记录；一次活动可由多名工程师参与并处理多台搬迁仪器，工作内容可包含拆机、装机、维修、其他。
- 开单记录：实际生成一份搬迁、认证、单寄备件或 PM 服务单据的业务记录；开单不等同于正式进单。
- 掉票记录：项目验收后按 ECC 向财务提交可确认金额的动作记录；掉票不等同于客户开票、回款或现场执行完成。
- 损坏/维修事项：一台搬迁仪器的一次运输损坏及其后续处理的整体记录；一个事项只对应一个备件（备件号、数量、金额），多个备件需分别建立事项。
- Ship-to：一处搬迁目的地址主数据；创建后不可修改，唯一编号为 Account ID（不是客户主账号）。
- Ship-to 申请：为系统外新址地址申请新增 Ship-to 的业务记录；只记录客户与新址地址，不关联搬迁仪器，不保存地址快照。
- 序列号地址更新：逐台登记搬迁仪器序列号实际关联新址的记录，含客户名称、新址地址、序列号、Account ID 与更新时间；不创建、修改或删除 Ship-to 主数据。
- 服务二维码：按搬迁仪器分别生成的外部二维码，内容为公司统一定制；工作台不保存二维码地址，仅由负责人按仪器手工标记"二维码是否申请"。
- 二维码申请：独立模块中的申请记录，保存申请人、申请时间与一个或多个申请类型（多选）；不关联搬迁仪器或搬迁项目。
- 待办：由系统按缺失信息自动生成的标准待办（七类），或由负责人新增的自定义待办。

### 5.3 汇总展示原则

1. 搬迁批次和搬迁项目只汇总展示所涉及的 Ship-to，不重复维护唯一的批次级或项目级地址。
2. 搬迁项目汇总各批次的运输安排和物流费用，不重复维护项目级物流明细。
3. 认证、单寄备件和 PM 开单记录独立保存，不进入搬迁项目生命周期。

## 6. 业务事件与项目生命周期

### 6.1 业务事件

- 正式进单（搬迁负责人确认接手项目）
- 开单（实际生成服务单据）
- 首次上门活动开始、首次搬迁批次开始运输
- 实际装机完成
- 验收报告形成（标记已有验收报告并填写报告形成日期）
- 掉票（按 ECC 向财务提交可确认金额）
- 项目取消

### 6.2 主状态与标签

1. 搬迁项目主状态依次为：待进单、待执行、执行中、待验收、待掉票、已完成；终止的项目标记为已取消。
2. 主状态由业务事实与动作推导，负责人不可直接手工编辑主状态。
3. "未进单先执行"等异常作为独立标签，可与主状态同时存在（存在该标签时主状态保持待进单）。
4. "已完成"表示掉票金额闭环（见 6.4）。

### 6.3 状态转移条件

| 当前状态 | 触发条件 | 目标状态 |
| --- | --- | --- |
| 待进单 | 正式进单（满足进单核心条件）且尚未发生实际执行活动 | 待执行 |
| 待执行 | 首次上门活动开始，或首个搬迁批次开始运输；仅完成排期、工程师或运输公司安排不算开始执行 | 执行中 |
| 执行中 | 负责人录入实际装机完成时间 | 待验收 |
| 待验收 | 标记已有验收报告并填写报告形成日期；不需要客户确认 | 待掉票 |
| 待掉票 | 累计掉票金额达到项目最终可确认金额 | 已完成 |
| 待掉票 / 已完成 | 掉票或最终可确认金额修改后，按累计金额与最终可确认金额在两者之间重算 | 按重算结果取待掉票或已完成 |
| 任一未取消状态 | 项目无任何掉票历史（含已撤销），并记录取消时间与原因 | 已取消 |

> 注：计划上门时间、计划运输时间与场地确认不触发主状态流转，仅用于决定对应标准待办的关键日期；进入待验收仅以实际装机完成时间为准。若正式进单前已发生实际执行活动（未进单先执行），进单后主状态按已发生事实跳到待执行、执行中或待验收（见 6.6）。

### 6.4 "已完成"的判定口径

1. 项目"已完成"表示掉票金额闭环：累计掉票金额达到项目最终可确认金额即进入已完成。
2. 未完成的损坏维修、未完成的 Ship-to 申请、仪器"二维码是否申请"未标记等事项**不阻塞**项目的进单、执行、验收、掉票或完成。
3. 未完成的损坏维修可在项目验收、掉票或完成后继续处理；Ship-to 申请未完成时仅显示为独立待办。
4. 首版不追踪财务审批、驳回或客户回款状态。

### 6.5 取消

1. 无任何掉票历史（含已撤销掉票）的任一未取消主状态均可取消；取消时必须记录取消时间和原因。
2. 存在任何掉票历史（含已撤销掉票）的项目禁止取消。
3. 已取消项目不可恢复；已取消状态期间禁止修改合同金额、最终可确认金额与掉票记录。
4. 已取消项目保留已经发生的上门活动、物流和费用记录；真实物流费用与损坏维修备件金额作为实际成本保留并计入对应统计，同时标记为已取消项目。
5. 已取消项目排除在项目管道、进单金额（收入）、掉票金额与掉票次数及金额闭环等收入与掉票指标之外。

### 6.6 未进单先执行的状态跳转

1. 核心信息未齐时，经经理批复可在正式进单前优先安排上门；在原搬迁项目上记录经理批复、原因及缺失项，主状态保持待进单。
2. 补齐核心资料完成正式进单后，按已发生事实将主状态推导为待执行（尚未执行）、执行中（已发生首次上门/运输）或待验收（已录入实际装机完成时间），不新建项目（规则暂定，见 TBD-08）。

## 7. 子流程

### 7.1 进单与未进单先执行

**正式进单时间规则**

1. 正式进单是搬迁负责人补齐必要信息并正式确认接手搬迁项目的业务事件，与开单是两个不同事件。
2. 进单时间在正式进单时必填，默认取当前时间，允许补录或修正；负责人填写的进单时间保持其填写值，不以当前时间覆盖；待进单或未进单先执行阶段可空。
3. 进单时间与系统创建时间分开记录，并作为进单统计口径。
4. 正式进单至少需要关联合同、客户单位并明确搬迁范围；任一缺失拒绝进单并生成"缺进单核心资料"标准待办。
5. 最终搬迁地址、工程师、运输公司和费用允许在进单后补充；各缺失项是否形成标准待办、对象粒度、生成/完成条件与关键日期按 7.7 逐类规则执行，不笼统承诺所有缺失立即生成待办。
6. 核心信息未齐时，经经理批复可在正式进单前优先安排上门；在原搬迁项目上标记"未进单先执行"，记录经理批复、原因及缺失项。
7. 后续在原项目上补齐正式进单所需核心信息并完成进单，不新建正式项目；进单后主状态按已发生事实跳转（见 6.6）。

**新建项目四步向导**

- **步骤 1 基本信息**：进单时间、区域、旧址联系人、新址联系人、合同开始日期与合同截止日期；不包含项目负责人或销售通知时间。合同截止日期不得早于合同开始日期，否则拒绝保存并提示。
- **步骤 2 搬迁范围**：旧址地址、新址地址、仪器名称（必填）、型号（选填）、UPS 是/否；不保存 Ship-to 地址快照。
- **步骤 3 执行准备**：计划上门时间与计划运输时间（分开记录）、场地确认、实际装机完成时间、服务单号（选填）。允许留空后补的字段在保存时不无提示丢失未填写内容；仅在满足 7.7 标准待办既有逐类规则时生成对应标准待办（如缺工程师、缺运输公司），实际装机完成时间在执行前为空不生成待办。
- **步骤 4 确认方式**：展示录入摘要，支持保存为待进单、正式进单、未进单先执行三个确认路径；保存为待进单时建立合同草稿并分配内部 ID 与系统临时编号。

**步骤 3 服务单号与开单创建**

- 服务单号选填；填写并保存且已选定参与工程师时，项目与自动创建的关联该搬迁项目的搬迁开单记录在同一保存操作中一并保存（原子保存），实际生成日期默认取当前时间，备注可空并允许后补。
- 填写单号但未选定工程师时，拒绝保存整个向导（项目本身也不保存）并就地提示先补齐工程师；不填写单号时不创建任何开单记录。
- 实际装机完成时间录入后，项目主状态推导为待验收；计划时间与场地确认不触发状态流转。

### 7.2 开单记录

1. 开单与正式进单是两个独立业务事件；开单不影响项目进单状态与主状态。
2. 开单记录区分搬迁、认证、单寄备件、PM 四类业务。
3. 搬迁开单关联对应搬迁项目；认证、单寄备件和 PM 开单独立保存，不进入搬迁项目生命周期。
4. 非空服务单号全局唯一，不同业务类型共用同一唯一空间。
5. 认证、单寄备件与 PM 开单至少记录类型、服务单号、生成日期、客户与工程师字段；备注允许后补，不属必填。
6. 开单工作量按唯一服务单号计数，同一服务单关联多名工程师或多次上门时仍只计一次，并按四类业务类型分组。

### 7.3 搬迁批次与物流

1. 运输公司记录在搬迁批次上；同一搬迁项目的不同批次可使用不同运输公司。
2. 批次保留原价与折后价，均以人民币记录，有值时必须大于 0；报价阶段不作为客户侧物流收入。
3. 每批次仅有一笔实际物流费用记录，归属于该批次；登记日期必填并默认当天，首次登记后决定归属月份，修改费用金额不改变登记日期与归属月份。
4. 实际物流费用记录必填三项人民币金额：预算价格、成交价格、物流费用；任一缺失、为 0 或负数时拒绝保存（金额有值必须大于 0）。
5. 成交价格大于预算价格时显示警告但允许保存，不生成标准待办、不阻塞批次运输或项目流转；系统展示成交价格与实际物流费用的差异。
6. 项目汇总各批次的运输安排和物流费用。

### 7.4 Ship-to 与 Ship-to 申请、序列号地址更新

**Ship-to 主数据**

1. 每处搬迁目的地址以 Ship-to 表达，唯一编号为 Ship-to ID（沿用现有字段名 Account ID），不是客户主账号；创建后不可修改，全部引用保持稳定。
2. 目的地址发生变化时重新申请新的 Ship-to，不更新或覆盖原记录。

**Ship-to 申请**

3. 系统中不存在目的 Ship-to 时，按同一客户、同一新址地址创建一条 Ship-to 申请；申请只记录客户名称与新址地址，不关联搬迁仪器，不保存结构化地址快照；客户或新址地址不同分别创建申请。
4. 申请创建时 Account ID 可空；由系统外完成流程返回后由负责人补入，补入的 Account ID 全局唯一（不得与已有 Ship-to 重复），补入后申请进入已完成并记录完成时间。
5. 申请独立采用待提交、处理中、已完成、已取消四种状态；每条申请在首次实际提交时计一次工作量，待提交草稿不计，退回重提不重复计数。
6. 申请未完成时只显示为独立待办，不阻塞搬迁项目的进单、执行、验收、掉票或完成。

**序列号地址更新**

7. 搬迁仪器实际迁往新址地址时，逐台登记一条序列号地址更新事实，记录客户名称、新址地址、序列号、Account ID 与更新时间；一台仪器可有多条更新事实表达多次地址变化。
8. 项目级新址地址仅作为默认计划，不自动成为每台仪器的实际关联新址；仪器实际关联新址以该仪器最近一条更新事实的新址地址为准。
9. 更新事实不得创建、修改或删除 Account ID 对应的不可变 Ship-to。
10. 更新时间必填、默认当前时间并可补录历史时间；客户名称、新址地址、序列号、Account ID 与更新时间为非空必填字段；序列号须与登记的搬迁仪器一致，不引入未确认的序列号格式约束。
11. 系统提供更新事实列表，支持按客户、新址地址、序列号、Account ID 或更新时间筛选，并按更新时间所属月份计数。

### 7.5 损坏、维修与备件

1. 一台搬迁仪器的一次运输损坏建立一个损坏/维修事项并关联该仪器；一个事项仅包含一个备件（备件号、数量、金额），同一损坏涉及多个备件时按备件分别建立多个事项，一个事项不得承载多个备件。
2. 事项记录字段：损坏原因、处理状态、备件号、数量、金额、维修过程备注；维修上门等处理过程记录在维修过程备注中。
3. 处理状态为未处理、处理中、已修复、已关闭未修复；选择已关闭未修复时必须记录原因。
4. 备件金额保留原币金额与币种（仅 USD 或 RMB）；RMB 金额固定按 1 USD = 7.2 RMB 折算为 USD 用于维修费用占比，不随年度变化，首版不接入实时汇率服务。金额必须有值且大于 0。
5. 损坏/维修事项独立于搬迁项目生命周期；未完成处理不阻塞项目的进单、执行、验收、掉票或完成，并可在这些阶段之后继续处理。
6. 维修报表按事项记录数量、单条记录的备件金额及合同占比统计：合同占比 = 单条记录金额 ÷ 合同 USD 含税金额；合同金额为空或零时不可计算并明确提示；占比超过 100% 允许如实显示并给出警告。

### 7.6 服务二维码与二维码申请

1. 每台搬迁仪器的"二维码是否申请"为负责人手工维护的是/否字段；不保存二维码地址（URL），不由二维码申请记录推导，也不自动生成"缺二维码"待办，不阻塞上门、运输或项目状态流转。
2. 二维码内容由公司统一定制，包含拆机报告、装机报告和序列号收集模块。
3. 二维码申请作为独立模块维护，与搬迁仪器和搬迁项目解耦：每条申请记录保存申请人、申请时间与一个或多个申请类型（多选），申请类型沿用九类固定代码（A、B、C、D、仅打包搬运精密仪器、OEM 设备、临时标签、项目验收单、物流管理）。
4. 二维码申请工作量按申请记录 × 去重后的选中类型计数：一条记录内每个去重后的选中类型各计一次，同一条记录内相同类型只计一次，不同申请中的相同类型分别计数；重复申请保留完整历史。
5. 项目快速记录入口不含二维码申请；二维码申请通过独立模块入口维护。

### 7.7 待办与提醒

1. 系统根据缺失信息和项目流程阶段自动生成标准待办，清单仅限七类：缺进单核心资料、缺可后补字段、缺目的地址/Ship-to、缺工程师、缺运输公司、Ship-to 申请未完成、批次运输后缺物流费用记录；同时允许搬迁负责人新增自定义待办。仪器"二维码是否申请"未标记或为否时不生成任何标准待办（见 7.6）。"缺目的地址/Ship-to"仅在搬迁仪器已存在实际装机工作事实/进度且尚无包含 Account ID 的有效序列号地址更新记录时生成；仪器实际装机为空、尚未开始装机时不生成，仅拆机已开始或运输已开始但尚未装机也不因该规则生成。
2. 标准待办按当前业务事实派生，不保存完成历史；缺失条件持续满足时保持唯一、不重复生成，缺失消除后自动完成并从列表消失，同一对象再次缺失时重新生成。自定义待办由负责人手工完成或取消。
3. 标准待办绑定相应业务关键日期判断逾期，没有关键日期时不标记逾期；自定义待办由负责人设置截止时间。
4. 批次成交价格高于预算仅显示警告，不生成标准待办。
5. 首版仅在工作台内展示待办提醒，不接入邮件、企业微信等外部消息渠道。
6. 临期范围由搬迁负责人自行配置；截止日当天归为今日到期，超过截止日归为已逾期。
7. 负责人未配置临期范围时，默认使用未来 7 个自然日。

## 8. 金额与币种规则

### 8.1 金额表达与正数规则

1. 所有金额以两位小数的十进制定点表达，保存与统计按四舍五入处理，全程不采用二进制浮点参与金额计算。
2. 所有录入金额（合同 USD 含税金额、最终可确认金额、掉票金额、批次原价/折后价、预算价格/成交价格/物流费用、损坏维修备件金额等）有值时必须大于 0，不得为 0 或负数；不允许 0 金额闭环（如 0 元掉票、0 元最终可确认金额）。

### 8.2 合同金额

1. 合同 USD 含税金额由搬迁负责人手工录入，不根据合同净值和税率自动计算；手工值与此前填写的净值和税率计算结果不一致时显示警告但允许保存，不自动覆盖手工值。
2. 正式进单时保存合同 USD 含税金额快照，该快照仅用于进单金额统计；后续合同变更不改写历史快照，最新合同金额用于当前项目展示和维修费用占比。
3. 合同变更标记为正式合同变更时，记录变更日期与原因（外部变更编号可选），并默认同步项目最终可确认金额；最终可确认金额已被人工调整时需明确选择是否同步，无论何种选择都记录相应原因。

### 8.3 项目最终可确认金额与掉票

1. 项目最终可确认金额默认取合同 USD 含税金额，允许搬迁负责人调整；任何调整必须记录原因。最终可确认金额不得低于累计掉票金额。
2. 新增掉票记录后累计金额不得超过项目最终可确认金额；确需增加时应先调整最终可确认金额并记录原因，再登记掉票。
3. 掉票支持分次记录，每次分别记录掉票时间和金额；掉票日期和金额允许直接覆盖修改，不保留旧值和更正原因，但自动记录最后修改时间，并据此重新计算统计结果。
4. 掉票记录不可物理删除，只能撤销；撤销必须记录撤销时间和原因，撤销后该记录不再计入掉票金额与掉票次数，并重新计算统计结果与项目状态。
5. 项目已处于待掉票或已完成时，掉票或最终可确认金额修改后按累计金额与最终可确认金额在两者之间重算；项目未处于待掉票或已完成时，金额修改不改变主状态。
6. 项目处于已取消状态期间，禁止修改合同金额、最终可确认金额与掉票记录。

### 8.4 备件币种与折算

1. 损坏/维修事项的备件金额保留原币金额与币种（仅 USD 或 RMB）。
2. RMB 备件金额固定按 1 USD = 7.2 RMB 折算为 USD 用于维修费用占比，不随年度变化；首版不接入实时汇率服务，其他币种暂不支持。

> 注：已取消项目排除在项目管道、进单金额（收入）、掉票金额与掉票次数及金额闭环等收入与掉票指标之外；取消前实际发生的物流费用与损坏维修备件金额作为真实成本保留并计入对应统计，并标记为已取消项目。各工作量指标的责任人取对应动作记录中的负责人，不依赖项目负责人字段或登录账号。
> 注：报表支持按月份区间、区域、开单业务类型与运输公司筛选（开单量另可按参与工程师筛选，可选），未选择筛选条件时默认展示当前季度；指标支持下钻查看支撑明细，实时计算不保存历史快照，仅支持 CSV 导出。

## 10. 存量数据迁移

1. 存量迁移由工作台外的部署运维人员作为一次性维护动作执行；工作台不提供任何迁移或导入入口，也不持续向用户提供导入功能。
2. 合同字段以合同信息表为主要来源，执行字段以项目执行表为主要来源，开单、掉票等动作记录以工作量统计表为主要来源；供应商与物流费用历史记录分别以供应商表、物流公司信息费用表为来源。
3. 记录识别以业务键（ECC、服务单号、Account ID、序列号）优先，无业务键时以源文件 + sheet + 行号兜底；无法明确拆分的旧数据保留未分批状态并进入冲突清单。
4. 同一字段在多个来源中取值冲突时不自动覆盖，生成冲突清单由搬迁负责人确认。
5. dry-run 为只读预演，不写入任何数据；对目标必填字段缺失的行输出错误，错误须指明源文件、sheet、行号与缺失字段；客户修正源 Excel 或通过补录模板补齐缺失字段后重新执行 dry-run 与正式导入。
6. 存在目标必填字段缺失错误的行不导入；目标可选字段允许为空，缺失不构成错误。
7. 正式导入前不得存在错误；每个导入批次作为一个整体提交或整体回滚，批次内任一记录失败时不产生部分数据（整批事务，不部分导入）；成功导入的批次以同一来源重跑时不重复写入；已提交的错误数据仅通过修正后重跑（forward-fix）纠正，不依赖反向回滚。
8. 历史项目状态由导入的事实经同一推导规则确定性重建，不要求也不允许在导入时手工指定项目状态。
9. 导入时间只作为审计字段保存，绝不替代源业务时间；源业务时间（掉票时间、开单生成日期、实际物流费用登记时间、进单确认时间等）映射到对应业务字段，缺失时保留为空，不用导入时间填充；该业务时间为目标必填字段时由 dry-run 报错且该行不导入。
10. 迁移覆盖新增字段或新增模块时不猜测映射（不按备注、相似文本或旧字段推断），无法明确映射的新增字段或模块进入冲突清单由负责人确认。
11. 导入后不存在"待补必填字段"流程，工作台不提供任何补录入口。

## 11. 数据校验与修改规则

1. 所有录入金额有值时必须大于 0，不得为 0 或负数；金额以两位小数的十进制定点表达并四舍五入（见 8.1）。
2. 手工 USD 含税金额与净值、税率计算结果不一致时显示警告但允许保存，不自动覆盖手工值。
3. 正式进单核心资料（合同、客户单位、搬迁范围）任一缺失拒绝进单，并生成"缺进单核心资料"标准待办。
4. 向导步骤 3 填写服务单号时，参与工程师必填：未选定参与工程师则拒绝保存整个向导（项目本身也不保存）并就地提示先补齐工程师；填写且已选定参与工程师时项目与自动创建的搬迁开单同次保存，实际生成日期默认取当前时间，备注可后补。
5. 合同截止日期不得早于合同开始日期，否则拒绝保存并提示。
6. 新增掉票记录后累计金额不得超过项目最终可确认金额；确需增加时先调整最终可确认金额并记录原因。
7. 调整项目最终可确认金额时必须记录原因；最终可确认金额不得低于累计掉票金额。
8. 掉票日期和金额允许直接覆盖修改；不保留旧值和更正原因，自动记录最后修改时间并据此重新计算统计结果；掉票只可撤销不可删除，撤销必须记录撤销时间与原因。
9. 物流费用登记日期必填并默认当天，修改金额不改变登记日期与归属月份；成交价格大于预算价格时显示警告但允许保存。
10. 损坏/维修事项选择"已关闭未修复"时必须记录原因；备件金额必须有值且大于 0。
11. Ship-to 创建后不可修改；目的地址变化时申请新 Ship-to，不更新或覆盖原记录。
12. 序列号地址更新事实的客户名称、新址地址、序列号、Account ID 与更新时间为非空必填字段；序列号须与登记的搬迁仪器一致。
13. 项目取消必须记录取消时间和原因；存在任何掉票历史（含已撤销）的项目禁止取消；已取消项目不可恢复、禁止修改金额与掉票记录。
14. 正式进单后 ECC 必填；ECC 全局唯一，正式进单后的更正通过唯一性校验并自动记录最后修改时间。

## 12. 运行与持久化边界

以下为已确认的首版边界（TBD-16 已解决，对应 ADR `docs/adr/0001-windows-desktop-local-sqlite.md`），不属待确认项：

1. 首版仅个人使用，仅支持 Windows 桌面，以桌面应用形态运行（Electron + React + TypeScript）。
2. 全部业务数据持久化在本机 SQLite 数据库中；关闭并重新打开应用后数据保留。
3. 不接入远程数据库、云同步或外部业务系统；首版不向任何远程服务发送业务数据。
4. 应用不提供应用内登录、注册、密码或角色权限体系；启动后依赖 Windows 操作系统当前登录用户账户访问本机数据。
5. 应用在每日首次使用时，若当天尚无自动备份，自动创建一份备份；自动备份仅保留最近 7 份，更旧的自动备份被清理。
6. 支持负责人立即手动备份到所选本地目录；手动备份不受最近 7 份数量限制。
7. 支持从负责人所选本地备份恢复；恢复前需确认并验证备份可读，恢复失败不得覆盖当前数据。
8. 备份或恢复失败时给出明确错误提示，不静默视为成功。
9. 系统升级涉及数据结构变更时，通过数据迁移保留现有本地数据；迁移失败时保留可恢复状态，不静默丢弃或损坏现有数据。
10. 上述边界不规定具体数据目录、文件布局或数据库实现细节。

## 13. 验收场景

以下场景均由已确认规则可直接验证：

1. **进单时间口径**：正式进单时进单时间必填，默认取当前时间并允许补录或修正；负责人填写的值不被当前时间覆盖；待进单或未进单先执行阶段可空；进单金额按进单时间所属月份归属统计。
2. **向导步骤 1 基本信息**：新建项目向导步骤 1 展示进单时间、区域、旧址联系人、新址联系人、合同开始与截止日期，不包含项目负责人或销售通知时间；合同截止日期早于开始日期时拒绝保存。
3. **向导步骤 2 搬迁范围**：展示旧址地址、新址地址、仪器名称（必填）、型号（选填）、UPS 是/否，不展示 Ship-to 地址快照；未填写仪器名称时拒绝保存。
4. **向导步骤 3 执行准备**：计划上门时间与计划运输时间分开记录，并分别记录场地确认、实际装机完成时间与服务单号（选填）；留空的可后补字段仅在满足 7.7 逐类规则时生成对应标准待办，实际装机完成时间在执行前为空不生成待办，未填写内容不无提示丢失。
5. **向导单号自动创建搬迁开单**：填写选填服务单号且已选定参与工程师时，项目与自动创建的搬迁开单记录同次保存，实际生成日期默认当前时间，备注可后补；填写单号但未选定工程师时拒绝保存整个向导并就地提示先补齐工程师；不填写单号时不创建开单。
6. **实际装机完成进入待验收**：录入实际装机完成时间后项目进入待验收；计划上门/运输时间到期或场地已确认不触发状态流转。
7. **未进单先执行**：核心信息未齐且经经理批复后可优先安排上门；原项目标记"未进单先执行"并记录批复、原因及缺失项，主状态保持待进单；补齐后在同一项目完成进单并按已发生事实跳到待执行、执行中或待验收。
8. **开单独立性**：开单与正式进单是两个不同业务事件，开单不影响进单状态与主状态；非空服务单号全局唯一。
9. **开单工作量**：同一服务单号无论关联多少名工程师或多少次上门，开单量只计一次，按搬迁、认证、单寄备件、PM 四类业务类型分组。
10. **批次报价与物流**：批次保留人民币原价与折后价（有值必须大于 0）；每批次仅一笔实际物流费用，登记日期必填默认当天；预算价格、成交价格、物流费用三项人民币金额必填且大于 0；成交价格大于预算价格时警告但允许保存，并展示成交价格与实际费用差异。
11. **Ship-to 不可变**：Ship-to 创建后不可修改；目的地址变化时重新申请新的 Ship-to，不更新或覆盖原记录。
12. **Ship-to 申请解耦**：申请只记录客户名称与新址地址，不关联搬迁仪器、不保存地址快照；创建时 Account ID 可空，系统外完成后补入全局唯一的 Account ID 并进入已完成；每条申请首次实际提交计一次工作量，待提交草稿不计、退回重提不重复计数。
13. **序列号地址更新**：逐台登记更新事实（客户名称、新址地址、序列号、Account ID、更新时间），更新时间默认当前并可补录历史；提供列表与筛选并按更新时间所属月份计数；不创建、修改或删除不可变 Ship-to；序列号须与登记仪器一致。
14. **损坏维修合并单单备件**：一个事项仅含一个备件，同一损坏多个备件分别建立事项；备件金额保留 USD/RMB 原币，RMB 按 1 USD = 7.2 RMB 折算用于占比；合同占比 = 单条事项金额 ÷ 合同 USD 含税金额，合同金额为空或零时不可计算，占比超过 100% 允许显示并给出警告。
15. **二维码是否申请手工**：仪器"二维码是否申请"为手工是/否字段，不保存二维码地址、不由申请记录推导、不自动生成"缺二维码"待办、不阻塞上门、运输或项目状态流转。
16. **二维码申请独立模块**：每条申请记录申请人、申请时间与多选类型（九类固定代码）；工作量按申请记录 × 去重后的选中类型计数，同一条申请内相同类型只计一次、不同申请中的相同类型分别计数；不关联搬迁仪器或搬迁项目；项目快速记录不含二维码申请。
17. **取消规则**：无任何掉票历史（含已撤销）的任一未取消状态可取消（必须记录取消时间与原因）；存在任何掉票历史（含已撤销）禁止取消；已取消项目不可恢复、禁止修改金额与掉票；收入与掉票指标排除已取消项目，真实物流费用与备件成本保留并标记取消。
18. **金额正数规则**：所有录入金额有值必须大于 0，无 0 闭环；掉票金额为 0 或负数、最终可确认金额低于累计掉票金额均拒绝保存。
19. **掉票闭环重算**：累计掉票金额达到最终可确认金额进入已完成；掉票修改、撤销或最终可确认金额修改后在待掉票与已完成之间重算；项目未处于待掉票或已完成时金额修改不改变主状态。
20. **迁移 dry-run 与整批事务**：dry-run 对目标必填字段缺失输出源文件、sheet、行与字段错误；客户修正源 Excel 或通过补录模板补齐后重跑；正式导入前不得存在错误；每个批次整体事务、不部分导入，同源重跑不重复写入；可选字段可空；工作台无迁移与补录入口；导入时间只作审计字段，不替代源业务时间。
21. **待办逾期与临期**：七类标准待办按缺失条件自动生成、按补齐条件自动完成；截止日当天为今日到期、超过截止日为已逾期；未配置临期范围时默认未来 7 个自然日；成交高于预算仅警告、不生成标准待办；仪器"二维码是否申请"未标记或为否时不生成任何标准待办。

### 15.3 早期记录与现行规则的主要差异（供评审追溯）

| 早期记录 | 早期表述 | 现行规则 |
| --- | --- | --- |
| 销售直接录入 | 销售与客户沟通后直接录入合同明细 | 首版仅搬迁负责人维护数据；销售无独立账号或录入入口 |
| 销售通知时间 | 销售通知时间可单独记录，不作为进单时间或进单统计口径 | 销售通知已取消，工作台不再记录销售通知（已取代） |
| 项目负责人字段 | 首版保留项目负责人字段，工作量归属其名下 | 项目负责人字段已取消，工作量归属责任人取动作记录中的负责人（已取代） |
| 进单 = 开单 | 确认进单后记录到开单记录表并视为进单 | 进单与开单是两个独立业务事件；开单分搬迁、认证、单寄备件、PM 四类 |
| 项目级二维码 | 生成服务二维码扫码查看整个项目执行情况 | 服务二维码按搬迁仪器分别生成，内容为公司统一定制模板；工作台只按仪器手工标记"二维码是否申请" |
| 两阶段工作流 | 执行分"执行前/执行后"两个阶段 | 采用待进单至已完成的主状态生命周期，并支持"未进单先执行"等独立标签 |
| 掉票 = 全部服务结束 | 执行后进行掉票即完成整个服务 | 掉票是项目验收后按 ECC 提交可确认金额的动作，不等同于回款或执行完成；项目"已完成"表示掉票金额闭环 |
| 工程师只有拆装 | 工程师涉及上门拆机和上门装机两部分工作 | 上门活动可包含拆机、装机、维修、其他工作类型 |
| 十张表即数据模型 | 以十张基础信息表作为数据结构 | 以第 5 章领域对象与关系模型为准，表清单仅作为早期输入 |
| 批次报价口径 | 原价、折扣、折后价、还价后最终报价（物流报价） | 批次仅保留原价与折后价（人民币）；实际物流费用记录预算价格、成交价格、物流费用三项（人民币），成交价格大于预算价格时警告（已取代） |
| Ship-to 申请关联仪器 | 一条申请按同一客户、同一目的地址聚合多台搬迁仪器 | Ship-to 申请只记录客户名称与新址地址，不关联搬迁仪器，不保存地址快照；Account ID 在申请完成后补入（已取代） |
| 独立备件申请 | 损坏/维修事项可关联多条备件申请，一张申请可含多条备件明细 | 损坏/维修事项合并单仅含一个备件，同一损坏多个备件分别建立事项；备件金额保留 USD/RMB 并按 7.2 折算用于占比（已取代） |
| 二维码申请关联项目 | 项目快速记录含二维码申请，申请对象指向搬迁仪器/项目验收单/物流管理 | 二维码申请为独立模块，只记录申请人、申请时间与多选类型，按记录 × 类型计数，不关联搬迁仪器或搬迁项目；项目快速记录不含二维码申请（已取代） |
| 二维码自动待办 | 仪器首次上门前未录入二维码地址时生成自动待办并持续提醒 | 仪器"二维码是否申请"为手工字段，不自动生成"缺二维码"待办（已取代） |
| 迁移字段标记待补 | 历史数据无法提供的字段保留为空并标记待补，工作台补录 | dry-run 对必填字段缺失报源文件/sheet/行/字段，客户修源 Excel/补录模板后重跑；正式导入前不得有错误；整批事务不部分导入；可选字段可空；无工作台补录（已取代） |
