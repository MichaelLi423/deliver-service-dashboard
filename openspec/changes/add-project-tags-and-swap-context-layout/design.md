## Context

本 change 的动机与可观察行为见 `proposal.md` 及各 capability delta spec。当前本地数据库 schema 版本为 v16，数据结构升级采用只追加迁移的方式；报表、下钻和导出共享筛选概念，renderer 仅可经 preload/IPC 访问主进程数据。本次需要同时改变本地持久化、项目编辑、报表筛选和工作台布局，因此需要在实现前固定跨层边界与迁移策略。

## Goals / Non-Goals

**Goals:**

- 在不混入项目主状态聚合的前提下，提供可复用的分组项目标签及项目多选关联。
- 以 v17 追加迁移安全保存标签数据，并为既有与恢复的数据库提供幂等预设标签初始化。
- 让报表构建、下钻和三种导出复用同一标签筛选语义且不重复计数。
- 用真实 DOM/JSX 结构移动交换项目详情与当前上下文，同时维持既有内容和联动。

**Non-Goals:**

- 不提供标签分组或标签的删除、重命名、重排能力。
- 不将标签存为 `projects` 中的 JSON，也不改变项目主状态、执行事实、提醒或生命周期规则。
- 不新增外部依赖、远程同步、down migration 或对旧二进制读写 v17 数据的兼容层。
- 不复制组件、以 CSS `order` 视觉调换位置，或重写项目详情、当前上下文的既有业务内容。

## Decisions

### 1. 使用规范化的三实体标签模型

v17 新增标签分组、组内标签定义、项目—标签多对多关联三类数据。分组名去除首尾空白后全局唯一；标签名去除首尾空白后在所属分组内唯一。显示顺序采用显式整数排序字段，再以稳定 ID 打破同序情况。设置项目标签时先对输入 ID 去重，并拒绝未知 ID。

该模型将全局标签目录与项目关联分开，支持同组及跨组多选、稳定展示和报表查询，也避免在项目记录中存放不可约束的结构化 JSON。

**Alternatives considered:** 将标签 JSON 存入项目记录可减少表数量，但无法可靠表达标签目录唯一性、复用关系和高效筛选，且不采用。仅允许每组一个标签会限制已确认的同组多选，不采用。

### 2. 追加单一 v17 迁移并在其中完成幂等预设初始化

在单一 v17 迁移事务中创建标签数据结构、必要索引和业务修订触发器，并以稳定 ID 幂等写入三组七个预设标签：项目类型（搬迁、PM、认证）、服务类型（暂存）、特殊仪器（LCMS TOF（65系列）、BSO、ICPMS）。迁移必须只追加在 v16 之后；不得修改历史迁移，也不得将新表接入历史迁移的触发器循环。重复 bootstrap 或升级不会重复插入预设分组和标签。

备份是数据库整体副本，因此自然涵盖新标签数据。恢复旧备份后，正常 bootstrap 将其从旧版本升级到 v17 并补齐预设数据。

**Alternatives considered:** 在应用每次启动时无版本控制地播种数据会使失败恢复和版本判断不明确，不采用。拆分为多个 schema 版本会扩大本次升级与验证范围，不采用。修改既有迁移会破坏已发布数据库的升级历史，不采用。

### 3. 标签作为独立分类模块，不进入生命周期状态聚合

标签目录与项目关联由 relocation-project-lifecycle 范围内的独立分类模块和关联仓储负责。创建项目携带 `tagIds` 时，项目事实和标签关联在同一原子保存中写入；编辑标签采用 replace-set 语义，使最终关联集合严格等于去重、验证后的输入集合。标签操作不调用 `lifecycle.ts`，不变更主状态、执行事实或提醒。

**Alternatives considered:** 将标签字段并入 Project 状态聚合会使分类写入经过状态转换路径并增加误触发风险，不采用。增量 add/remove API 会增加客户端同步与重复提交的状态复杂度，不采用。

### 4. 经语义化 IPC 暴露标签能力

共享 IPC 契约提供读取标签目录、创建标签分组、创建组内标签和设置项目标签的语义化接口。preload 仅暴露这些受控能力，renderer 不直接访问 SQLite。设置接口返回或刷新规范化项目标签视图，以便项目新建、编辑、队列、详情和当前上下文使用一致的数据。

**Alternatives considered:** renderer 直接读写数据库会违反既有运行边界，不采用。通用 SQL 或表级 CRUD IPC 会泄露持久化实现并扩大接口面，不采用。删除、重命名、重排接口超出已授权的自定义新增范围，不采用。

### 5. 报表以匹配项目集合执行标签筛选，避免事实重复

`ReportFilterDto` 增加 `tagIds`。`undefined` 或空数组不限制结果；非空时按 OR 语义选出包含任一标签的项目。报表层先构造唯一的 `matchingProjectIds` 集合，或在各事实查询中使用等价的 SQL `EXISTS` 条件；不得将项目—标签关联直接 JOIN 到聚合事实，以免一个项目的多个标签重复放大金额和计数。

标签筛选启用时，只有归属于匹配项目的事实进入统计；不关联任何项目的独立记录无法匹配，必须从指标、下钻和导出排除。报表构建、下钻和导出复用同一筛选构造，确保筛选口径一致。

**Alternatives considered:** 直接 JOIN 关联表后聚合实现简单，但会造成重复金额和数量，不采用。分别为汇总、下钻、导出实现标签条件会造成口径漂移，不采用。将独立记录视为“无标签项目”会违反标签筛选无法匹配项目的已确认口径，不采用。

### 6. 用真实 JSX/DOM 移动完成布局交换，并保留组件职责

调整工作台真实 JSX/DOM 层级为：提醒与项目详情、项目队列、当前上下文。项目详情移动到原当前上下文位置，当前上下文移动到原项目详情位置；保留既有组件实例和数据/事件联动，不复制组件或使用 CSS `order` 制造视觉交换。详情侧栏设置 `min-width: 0` 并在自身区域内部滚动；当前上下文移至队列后可采用横向分区，较窄桌面宽度改为堆叠。

布局验证覆盖 1440px、1024px 以及约 1180px 断点两侧，并检查键盘操作、项目/提醒/生命周期阶段联动和页面级横向溢出。

**Alternatives considered:** CSS `order` 不改变实际 DOM 阅读与焦点顺序，且会增加响应式维护歧义，不采用。复制项目详情或当前上下文以适配两个位置会导致内容和联动分叉，不采用。固定单列或固定三列不能同时满足 1024px 与较宽桌面可用性，不采用。

## Risks / Trade-offs

- [项目—标签关联直接 JOIN 聚合事实会重复金额或计数] → 在共享筛选构造中使用唯一项目 ID 集合或 `EXISTS`，并让汇总、下钻、导出共用它。
- [标签写入误触发生命周期] → 标签保持独立模块与仓储，设置标签不调用 `lifecycle.ts`，不写入状态、执行事实或提醒。
- [预设 seed 与历史迁移产生重复或破坏升级链] → 仅追加 v17，在同一事务内以稳定 ID 幂等 seed，不改写历史迁移或其触发器循环。
- [项目详情移入较窄区域后内容溢出或挤压队列] → 详情区域使用 `min-width: 0` 与内部滚动，并在约 1180px 断点及 1024px 堆叠布局验证核心操作。
- [旧 UI 持有已不存在或未知的标签 ID] → 设置接口对输入去重并拒绝未知 ID；目录刷新后 UI 仅提交当前有效标签。
- [旧二进制打开 v17 数据库] → 不支持降级读取；升级前保留 v16 备份，发生需要回退的情况从该备份恢复并使用对应旧二进制。

## Migration Plan

1. 发布包含 v17 追加迁移的版本；首次启动在单事务内执行结构创建、索引/业务修订触发器创建和预设标签幂等初始化。
2. 启动后按 v17 数据库读取标签目录、项目关联并启用标签筛选与新布局；现有项目保持无标签，标签筛选未启用时不改变既有报表结果。
3. 备份与恢复沿用现有完整数据库流程；恢复旧备份后 bootstrap 自动升级至 v17。
4. 若 v17 迁移失败，事务回滚并保留可恢复的 v16 数据库状态；不得继续以部分迁移状态运行。
5. 不提供 down migration。部署后如需回滚，停止使用新二进制产生的 v17 数据库，从迁移前保存的 v16 备份恢复，再启动旧版本二进制。
