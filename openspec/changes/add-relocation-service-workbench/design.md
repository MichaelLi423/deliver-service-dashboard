## Goals / Non-Goals

**Goals:**

- 提供可支撑 15 个能力规格的逻辑架构：模块化单体逻辑边界（与 15 个 capability 一致、可调整）、聚合边界与关系、稳定内部 ID 与业务 ID 分离。
- 以"集中状态校验入口 + 明确自动触发"为统一机制，使项目主状态的人工调整、实际装机完成/验收/金额闭环自动触发、取消约束都经由 lifecycle 唯一入口校验，避免各模块各自维护状态导致不一致。
- 让金额精度、掉票终态、Ship-to 不可变、迁移幂等/冲突/事务、备件处理状态等关键规则有明确、可定位的实现归属。
- 使历史数据导入成为登录后的工作台内向导：模板/文件/粘贴统一规范化、草稿修正与校验定位、validation seal 封存、七类数据一次全局原子提交，以 ECC 为聚合主键，并在不把 renderer 变成 Excel 处理进程的前提下支持至少 50,000 行输入与 100,000 行网格。
- 使本地数据具备可验证的持久化、备份与恢复路径（本地 SQLite、每日自动 7 份备份、手动备份/恢复与失败保护）。

**Non-Goals:**

- 不决定具体版本、打包器、ORM、SQLite 访问/迁移库、数据目录等实现细节（apply 前决策，见 Open Questions；已确认项见 tasks 0.2）。
- 不引入微服务、通用工作流/规则引擎、事件溯源、远程数据库、云同步或外部集成框架。
- 不做数据库/备份文件加密或云备份（本地账号仅为访问门槛、不加密 SQLite，超出已确认边界，见 D12/D17/D18）。
- 不做任何代码实现。
- 不重述业务范围、领域规则与能力内容（分别见 proposal.md 与后续 specs）；所有 25 项 TBD 已确认，不存在未决暂定决定。

## Decisions

每项决策给出选择、理由与被拒替代方案。业务判定均引用 proposal.md《客户最终答复》与 docs v0.3，本设计只承担其技术/逻辑含义。

### D1 稳定内部 ID 与业务 ID 分离

**选择**：每个聚合/实体由系统分配一个创建时生成、永不复用、不随业务变更的稳定内部 ID，作为全部引用与关联的键；ECC、服务单号、Account ID、仪器序列号、客户名称等业务 ID 作为独立字段保存，各自带可空与唯一性约束。客户名称（trim 后唯一）是客户对外唯一业务标识，系统内部可保留技术引用 ID（TBD-25）。

**理由**：业务 ID 的特征彼此冲突且与"引用稳定"冲突——ECC 在正式进单后才具备（TBD-01，待进单阶段仅临时编号）；服务单号要求全局唯一但迁移数据存在重复（TBD-21）；Ship-to 创建后不可修改（已确认）；序列号在合同/项目内唯一、跨合同可重复（TBD-02）；客户名称允许跨 ECC 项目复用（TBD-25）。内部 ID 与业务 ID 分离后，补 ECC、迁移纠错、撤销与状态重算都不会破坏既有引用。

**被拒替代**：以业务 ID 直接作主键（无法表达无 ECC 的待进单态，迁移冲突会使建库失败）；以客户名称直接作技术主键（同一客户名称可关联多个 ECC 项目，需支持多值引用）。

### D2 模块化单体逻辑边界（与 15 个 capability 一致）

**选择**：一个逻辑单体，内部按能力划分为模块，与 15 个 capability 一一对应；模块间通过进程内服务调用协作，共享一个领域内核（金额值对象、ID 规则、状态校验入口）。该边界是**逻辑接缝**而非独立部署或独立存储；apply 阶段可按实现便利调整，但不改变 15 个能力的外部行为与 spec 定义。

**理由**：单角色、小团队、无外部集成的规模下，单体是最简单直接的形态；边界与 15 份 spec 对齐，使每份 spec 有明确实现归属，可独立构建与测试，也为后续 tasks 提供拆分依据。

**被拒替代**：微服务（无独立扩展、独立团队或独立故障域需求，只增加运维与分布成本）；事件总线/事件源（proposal 明确排除事件溯源，且状态规则是封闭有限集，事件总线只增加间接性）；通用工作流/规则引擎（规则封闭有限，引擎引入额外抽象与学习成本，与 Non-goals 冲突）。

### D3 聚合边界与跨聚合关系

**选择**：

- **搬迁项目**为项目级聚合根；**合同**是该项目聚合内与项目 1:1 的独立领域对象（持有临时编号、正式 ECC、合同 USD 含税金额（允许 0）与进单金额快照、最终可确认金额）；待进单阶段合同可空、可不关联（TBD-01），正式进单前必须补齐合同；搬迁项目聚合根持有所属区域、未进单先执行标签、取消信息（不可恢复）、项目默认地址、项目提醒（当前提醒日期与备注）；项目聚合维护项目级不变量（正式进单必要条件、最终可确认金额 ≥ 累计掉票金额、金额不得为负、仅合同金额允许 0）。
- 以下为独立聚合，跨聚合引用一律使用稳定内部 ID（D1）：搬迁批次（与物流费用合并为一次记录：计划运输日期、运输公司、费用登记日期、合同预算价/物流成交价人民币、改批历史记录）、搬迁仪器（仪器名称、序列号、所属批次、目的 Ship-to、二维码手工标记）、上门活动（含"活动 × 仪器 × 工作类型"事实行，见 D5）、开单记录、Ship-to 申请（线性状态）、Ship-to（不可变主数据）、损坏/维修事项（聚合其下单个备件的备件号/数量/金额/备件申请日期/备件处理状态与维修过程备注）、序列号地址更新记录、二维码申请、掉票记录、客户主数据（客户名称为唯一业务标识）。
- 跨聚合不变量（如掉票累计与最终可确认金额的关系、合同金额 0 时的维修限制）不在各聚合内重复实现，由对应模块的领域服务在单一入口校验。

**理由**：一致性边界明确，避免"项目巨型聚合"使所有写操作互相锁定；项目提醒跟随项目聚合、随项目生命周期共存；改批历史作为批次聚合内的事件记录（TBD-03）。

**被拒替代**：项目聚合包住全部子对象（所有变更锁定全项目、耦合过高）；所有对象完全独立无聚合（不变量无处归属、关系散乱、难以保证金额闭环）。

### D4 集中状态校验入口（人工调整 + 明确自动触发）

**选择**：项目主状态由负责人**人工选择/调整**（TBD-09），relocation-project-lifecycle 模块是唯一拥有状态转换/校验入口的模块，但不是纯事实推导：负责人提交主状态修改时，lifecycle 校验（a）目标状态是否为合法状态之一；（b）取消约束（有掉票历史含已撤销不可取消；已取消不可恢复）；（c）以下明确自动触发优先于人工值——录入实际装机完成日期自动置为待验收（TBD-07），标记验收报告并填写报告形成日期自动置为待掉票，待掉票/已完成之间按累计掉票金额与最终可确认金额自动重算（TBD-11）。其他模块提供事实、调用该入口，不各自维护状态副本。

**理由**：TBD-09 已确认人工调整主状态；同时 TBD-07/验收/金额闭环是已确认的明确自动触发，二者必须在同一入口校验，避免人工值与自动触发互相覆盖产生不一致；单一入口保证状态、取消约束、金额闭环口径一致。

**被拒替代**：持久化状态列并完全自由修改（无法保证 TBD-07/验收/金额闭环自动触发与取消约束）；纯事实推导且不可编辑（已被 TBD-09 取代）；各模块各自计算状态副本（规则重复、结果分叉）。

### D5 活动 × 仪器 × 工作类型

**选择**：上门活动记录事实（到访日期、参与工程师）；工作内容表达为"活动 × 仪器 × 工作类型"的事实行——同一活动的同一台仪器可含多种工作类型（拆机、装机、维修、其他），同一活动可处理多台仪器，且在同一上门活动页面记录（TBD-05）；工作事实采用两态持久化：不存在对应工作事实即表示未开始，创建事实时状态为进行中并记录开始日期，完成后状态为已完成并记录完成日期。**拆机工作事实明确记录拆机状态及拆机开始/完成日期，其他工作类型记录各自状态与日期**（TBD-05）。仪器拆装进度由工作事实是否存在及其状态推导，不设可编辑的进度字段。活动×仪器工作事实行由 relocation-execution 拥有；维修上门活动同时关联损坏/维修事项，为多对多关系（TBD-24，该关联规则归属 damage-repair-tracking），并校验该事项所属仪器属于该活动的仪器集合。

**理由**：TBD-05 与 TBD-24——一次活动多类型、多仪器、可处理多事项，且拆机/装机/维修/其他类型在同一页面维护；拆机状态与开始/完成日期显式记录，其他类型记录各自状态/日期，使拆装进度可推导、可随事实修正重算；维修工作与损坏事项解耦（事项独立于生命周期、不阻塞状态流转）。

**被拒替代**：上门活动单一工作类型字段（无法表达多类型、多仪器）；拆装进度作为可编辑字段（无法从工作事实重算）；以仅存在工作事实记录即视为完成（记录存在但尚未完成时无法表达进行中）。

### D6 不可变 Ship-to、项目默认地址与逐台地址更新

**选择**：Ship-to 为不可变主数据，以 Account ID 标识，创建后禁止更新（目的地址变化 = 申请新 Ship-to）。Ship-to 申请仅记录客户名称与新址地址，不关联搬迁仪器、不保存结构化地址快照；申请创建时 Account ID 可空，由系统外完成流程返回后由负责人补入全局唯一的 Account ID，补入后申请进入已完成并记录完成日期（进入已完成前 Account ID 必填），补入的 Account ID 创建/对应不可变的 Ship-to。申请状态**线性流转**：待提交 → 处理中 → 已完成，不支持退回或取消（TBD-04）。搬迁项目设置项目默认地址，搬迁仪器默认沿用项目默认地址；实际仪器地址仅由序列号地址更新记录（serial-address-update 模块）逐台表达，该更新事实不修改 Ship-to 主数据。

**理由**：TBD-04——申请仅记录客户与新址地址，不关联仪器、不保存地址快照；线性状态不支持退回或取消，因此"退回重提不重复计数"场景自然不存在，首次实际提交计一次工作量；Ship-to 不可变是已确认规则，保证历史引用与统计稳定；Account ID 完成前必填保证已完成申请必有对应不可变 Ship-to。

**被拒替代**：原地修改 Ship-to（违反已确认规则、破坏历史引用）；申请保存结构化地址快照或关联搬迁仪器（与客户确认规则冲突）；支持申请退回或取消（与 TBD-04 线性状态冲突）；以项目默认地址直接作为所有仪器地址且不记录逐台更新（无法表达实际关联事实）。

### D7 金额十进制定点、精度、币种边界与固定汇率

**选择**：金额一律以十进制定点类型表达（物理表示为分整数，逻辑类型精确到分、两位小数，全程禁用二进制浮点）；舍入规则为四舍五入，且只在明确聚合点应用。**仅合同 USD 含税金额允许为 0**；其他录入金额（最终可确认、掉票、合同预算价与物流成交价、备件）有值必须大于 0、不得为负数，无 0 金额闭环（TBD-11）。合同金额与掉票/最终可确认金额以 USD 表达；合同金额为 0 时，正式进单的最终可确认金额不能默认成 0，必须另行录入大于 0 的值。物流与搬迁批次合并为一次记账——批次记录费用登记日期（必填默认当天、决定归属月份、后续不修改）、合同预算价与物流成交价（人民币，均必填且大于 0），运输公司可选，不做 USD 记账，物流成交价即最终实际物流费用，物流成交价大于合同预算价仅警告；物流成交价按固定常量 `1 USD = 7.2 RMB` 折算 USD 后除以最新合同 USD 含税金额展示**物流费用合同占比**（TBD-14），合同金额空/0 时不可计算并提示。历史导入仍兼容旧"预算/成交/实际费用"三列数据，但不是当前录入模型；历史批次缺费用视为异常数据、不提供独立补录入口。备件金额仅 USD/RMB，RMB→USD 按固定常量折算，仅"已使用"备件金额计入维修费用与占比（TBD-13）。

**理由**：TBD-11/13/14 已确认的精度、正数与 0 值边界；合同金额允许 0 但其他金额必须 > 0，最终可确认金额在合同 0 时不得默认 0；固定汇率避免多币种折算歧义；保留原币可追溯；仅"已使用"备件计维修费用使占比口径与备件实际投入一致。

**被拒替代**：浮点（累计与占比精度漂移）；所有金额一律 > 0（与"仅合同金额允许 0"冲突）；只存 USD 折算值（丢失原币金额，无法复核）；接入实时汇率（proposal 明确不做）；保留独立"实际物流费用"金额与独立批次报价层（客户确认合并为一次记录，物流成交价即最终实际物流费用）；全部备件金额一律计入维修占比（与"仅已使用"冲突）。

### D8 掉票终态与金额闭环重算

**选择**：掉票记录不允许物理删除；撤销通过记录撤销日期与原因的撤销动作实现，撤销后为**终态**——禁止编辑、重复撤销或重新激活，更正需新增有效掉票（TBD-19）；撤销后不计金额与次数。掉票日期和金额允许直接覆盖修改（仅未撤销的有效掉票），系统自动记录最后修改时间（审计/技术时间，精确 ISO；不保留旧值）。任何掉票新增/编辑/撤销或最终可确认金额调整后，由 D4 的 lifecycle 校验入口按"累计掉票金额 vs 最终可确认金额"在待掉票/已完成之间重算（TBD-11），并同步重算相关报表聚合。新增掉票累计不得超出最终可确认金额，超限时先调整最终可确认金额。取消规则（TBD-10）：任何无掉票历史（含撤销）的未取消主状态项目均可取消，取消不可恢复，继续工作需重新新增项目；取消必须记录取消日期与原因并保留已发生的上门活动、物流与费用记录；取消期间禁止修改合同金额、最终可确认金额与掉票记录。

**理由**：TBD-19——掉票撤销后终态，禁止编辑/重复撤销/重新激活，更正新增有效掉票；TBD-11 的闭环重算与 0 值边界、TBD-10 的取消规则已确认；撤销动作保留时间与原因，使统计重算和审计链确定。

**被拒替代**：物理删除（违反 TBD-19，删除后统计与状态无依据）；撤销后允许重新激活或再次撤销（与终态冲突）；对每次编辑保留完整历史版本（proposal 明确"不保留旧值和更正原因，只记最后修改时间"，属已接受业务取舍，见 Risks R5）。

### D9 项目提醒（手工维护，非派生）

**选择**：删除七类自动标准待办与自定义待办的整套派生/自动完成/关键日期规则（TBD-23）。**项目提醒**是搬迁项目聚合内的手工维护字段：每个搬迁项目一个当前提醒（当前提醒日期 + 备注内容），由负责人创建/编辑/清除，不保存提醒完成历史；系统不根据任何缺失字段自动生成提醒（成交高于预算、二维码未标记、Ship-to 申请未完成等均不自动创建提醒）。到期分类按提醒日期显示临期、今日到期或已逾期，临期窗口由负责人配置（默认未来 7 个自然日），截止日当天为今日到期、超过为已逾期；提醒仅在工作台内展示。workbench-todos 模块是项目提醒展示与到期分类规则的所有者，消费 lifecycle 的项目提醒字段与当天日期，不拥有业务状态。

**理由**：TBD-23——客户确认删除自动待办，改为负责人手工维护的项目提醒；主工作流从"自动待办"改为"项目提醒快速处理 + 项目队列"；到期分类是纯函数（提醒日期 vs 当天），不保存历史。

**被拒替代**：保留七类自动标准待办及其派生/自动完成/关键日期规则（已被 TBD-23 取代）；保留自定义待办概念（已并入项目提醒）；系统根据缺失字段自动生成提醒（与"完全手工维护"冲突）；各模块各自生成提醒（口径分叉）。

### D10 实时派生报表与三种导出

**选择**：报表（operational-reporting）按需实时从事实集合计算，不建报表快照表；**月份区间由负责人手工选择（无默认季度）**（TBD-17），区域、开单业务类型、运输公司、参与工程师等筛选维度可保留；导出支持 Excel（.xlsx）、图片（PNG）与 PDF，导出内容为当前筛选条件下的实时结果（TBD-17；导出技术库可留 apply 时选择，格式已定）。指标口径字典以 spec 为准，实现归属 reporting 模块，读取的事实与校验入口与其他模块共享。

**理由**：TBD-17 要求手工月份区间、实时更新与三种导出；掉票终态、取消（TBD-10）等事后变更都会影响统计，实时推导天然反映最新事实；仅"已使用"备件计维修费用、物流费用合同占比等新口径按 spec 实时计算。

**被拒替代**：默认当前季度（已被 TBD-17 取代）；仅 CSV 导出（已被 TBD-17 取代，现为 Excel/PNG/PDF）；定时快照/物化报表表（TBD-17 不做月结与报表快照，且掉票事后变更会造成快照过期）；引入 BI 工具（外部集成，Non-goal）。

### D11 历史数据导入：工作台内向导、ECC 聚合与七类一次原子导入

**选择**：历史数据导入以**登录后的工作台内向导**为唯一入口（位于"数据管理"，与手动备份/恢复并列），移除工作台外迁移 CLI 与"工作台不得提供导入入口"的旧约束。导入覆盖项目/合同、开单记录、掉票记录、物流费用、序列号地址更新、二维码申请和 Ship-to 申请七类历史数据，每类由用户明确提供数据或确认本次无数据、不得静默跳过。

**以 ECC 为项目/合同聚合主键**（TBD-18）：同一 ECC 下一个合同的全部执行数据均聚合导入并作为一个搬迁项目展示；服务单号、Account ID、序列号用于子记录识别与冲突处理，**不与 ECC 同级匹配项目**；掉票与物流费用必须引用本次计划或目标库中唯一匹配的 ECC，二维码申请与 Ship-to 申请不因缺少 ECC 被强制关联项目。输入统一为版本化规范化模型：模板、`.xlsx` 文件与 Excel 矩形复制粘贴进入同一套目标字段、列映射与目标网格；自动映射只接受当前模板字段及冻结别名，不做相似名称模糊匹配；ECC、服务单号、Account ID 与序列号始终按文本处理以保留前导零（详见 D21/D22）。

校验分三级（阻断错误、待解决冲突、非阻断警告），错误与冲突全部解决后才能生成可提交的校验封存（validation seal，D25）；校验阶段对正式业务表零写入，输入、修正与校验状态只保存在与正式业务库隔离的导入草稿工作区（D20），用户可保存退出后继续。最终提交将七类计划记录、来源审计、目标快照与成功运行审计作为一个不可分割的单元，在一个正式业务事务中提交（D26），任一记录、审计或写后对账失败整体回滚，不保留部分导入。

保留来源键、来源摘要与目标快照机制：相同计划摘要重跑不重复写入；来源键相同、内容修正且目标快照未变时允许安全 forward-fix；目标记录被人工创建、导入后人工修改或缺少可信基线时阻止覆盖。历史项目状态由导入事实按现行生命周期规则确定性重建，导入不提供直接指定主状态的字段；源业务日期保存到对应业务字段，导入时间仅用于审计、**绝不**替代源业务日期。迁移运行审计归属最终确认的登录账号并保存确认时用户名快照（D27）；导入的业务事实标记为历史导入，不视为负责人手工录入、不计入确认账号的手工工作量。

**理由**：TBD-18/21 已确认 ECC 聚合主键、重复服务单号冲突、幂等、forward-fix 与源时间规则；用户最新决定将执行方式由工作台外脚本改为登录后的向导，使负责人能在工作台内直观看到字段映射、关联关系与最终导入范围，并通过草稿修正、错误定位与一次原子提交替代脚本的"改源重跑"循环；七类一次原子提交保证任意类别失败都不会留下部分导入。

**被拒替代**：以服务单号/Account ID/序列号与 ECC 同级匹配项目（与 TBD-18 聚合主键冲突）；缺 ECC 仍导入为未进单待办（与"缺 ECC 报必填错误"冲突）；持续导入功能与补录 UI（TBD-18 Non-goal，仅首版一次性迁移、不建补录 UI）；按文本相似度推断缺失字段（proposal 明确禁止推断）；保留按 ECC/standalone 分批提交并在 UI 汇总（允许前一项目成功、后一项目失败，不符合一次原子导入，D26 明确废弃）；工作台外 CLI 作为执行载体（与"向导为唯一入口"冲突）。

### D12 单一本地应用账号访问门槛与事实归属；不集成外部系统

**选择**：应用提供**单一本地应用账号**作为访问门槛，仅用于控制进入应用界面，不构成任何远程或多用户体系：

- **首次初始化**：首次启动必须创建用户名与密码，创建完成后禁止新增第二个账号；不提供多账号、注册、自助新增用户、角色与权限管理。**后续启动**必须登录该本地账号才能进入工作台；无远程认证、无外部身份源、无账号同步。
- **忘记密码**：通过账号初始化时生成的一次性恢复码重设；恢复码只展示一次、由用户离线保存，使用后失效并生成新的恢复码。**密码与恢复码不得明文存储**：使用 Node 内置 scrypt 配合每条记录独立的随机盐派生存储，校验使用 timingSafeEqual 恒定时间比较，不引入任何原生密码依赖。
- **事实归属**：负责人手工录入的外部业务事实归属当前已登录的本地应用账号；动作记录持久化账号内部 ID 与录入时的用户名快照（D1 内部 ID 与业务 ID 分离机制下为账号实体 ID + 用户名业务字段），历史统计不因以后用户名修改而动态变化；本规则不因仅有一个账号而省略。
- **访问门槛边界**：本地账号仅控制应用访问，不加密 SQLite 数据库文件；Windows 操作系统账户仍是本机数据文件与备份的主要保护边界，文档明确登录本地账号不能防止直接读取数据库文件。
- 不实现任何外部系统适配器与同步任务，不接入远程数据库或云同步（见 D17）。不设项目负责人字段。

本决策基于已确认的运行与持久化边界（TBD-16 已解决，2026-08-06 客户确认、访问边界 2026-08-07 修订），不再属暂定；密码哈希参数、账号数据存放位置与恢复码生命周期细节属 apply 前决策（见 Open Questions 与 tasks 0.2）。

**理由**：仅个人使用、单 Windows 桌面的边界下，单一本地账号为后续登录与事实归属提供最小归属载体，同时不引入多用户、角色、权限或远程认证的复杂度；密码与恢复码使用 Node 内置 scrypt + 随机盐 + 恒定时间比较，满足"不引入原生密码依赖"且不破坏离线单机边界；账号仅为访问门槛、不加密 SQLite，避免误称登录可保护数据库文件本身；事实归属快照保证历史统计稳定。

**被拒替代**：完全无应用内账号（无法表达手工录入事实与工作量的归属载体，已被客户决定取代）；应用内认证/权限体系（多账号、角色与远程认证超出首版边界，明确不做）；数据库加密或备份加密（超出已确认边界，Windows 操作系统账户承担数据文件保护）；接入外部身份源、远程数据库或云同步（与已确认边界冲突）。

### D13 客户名称唯一业务标识

**选择**：客户名称是客户唯一业务标识：去除首尾空白后全局唯一（TBD-25）；同一客户名称可关联多个不同 ECC 搬迁项目；系统内部保留技术引用 ID，但不记录客户外部编号，删除"客户名称可重复、外部编号唯一"的旧规则。ECC 是搬迁项目/合同全局唯一标识。客户主数据聚合按 trim 后客户名称唯一，各业务对象通过内部引用 ID 关联客户。

**理由**：TBD-25——客户名称为客户唯一业务标识，trim 后唯一，跨 ECC 项目复用；ECC 为项目/合同聚合主键（与 D11 一致）；删除外部编号避免双标识源。

**被拒替代**：客户名称允许重复 + 外部编号唯一（已被 TBD-25 取代，双标识源增加迁移与校验复杂度）；以客户名称为技术主键（同一名称跨 ECC 项目复用需要支持多值，内部 ID 更稳）。

### D14 任务指挥台主结构 + 生命周期吞吐 + 当前上下文

**选择**：工作台信息架构采用客户确认的组合方案——以 A「任务指挥台」为主，保留 B 的「生命周期吞吐」板块和 C 的「当前上下文」板块。设计来源为客户高保真录入原型 `prototype/relocation-workbench/selected/relocation-workbench-selected.html`（该原型是设计依据，不是生产代码，后续将更新，对应行为契约见 workbench-interface 规格）。主要区域为：顶部 KPI/任务入口（月度运营指标与**项目提醒快速处理**入口）、紧凑六阶段生命周期吞吐板块、高密度主项目队列、随选中项目/待办/阶段联动的常驻当前上下文侧栏、以及六个按需展开的详情 tab（项目总览、搬迁仪器、搬迁批次、上门活动、费用与掉票、申请与维修）。交互联动：点击项目行选中并刷新当前上下文与详情；点击项目提醒联动选中其所属项目并定位到详情；点击生命周期阶段筛选项目队列并选中该阶段内项目；详情 tab 在选中项目内按需切换。**未进单项目与已进单项目在界面中使用明确不同的颜色/视觉标识**（TBD-08）。本板块消费各领域模块既有事实与校验结果（D4），自身不维护业务状态，作为表现层模块纳入 D2 的逻辑接缝。

**理由**：**项目提醒快速处理与高密度项目队列构成主操作流**（TBD-23 将自动待办改为手工项目提醒），使负责人先处理临期/逾期提醒再连续处理项目；生命周期吞吐以紧凑阶段带补充全局节奏与瓶颈判断；当前上下文在选中项目时集中提供状态异常、当前提醒、金额闭环与非阻塞事项；未进单/已进单颜色区分（TBD-08）支持快速辨识；详情 tab 按需展开避免主工作区信息过载。该组合是客户已确认的界面决策，不属于 TBD 暂定范围，本设计不得改变其结构或擅自视觉重构；数据录入方式与视觉可用性基线分别见 D15 与 D16。

**被拒替代**：
- 以纯看板（B 项目流水线）为主界面：流动可视化虽直观，但降低高密度项目表的信息密度与连续操作效率，故仅以紧凑吞吐板块保留其全局节奏价值；
- 以纯单项目主从（C 主从工作区）为主界面：围绕单个项目深度处理会弱化提醒与项目队列的全局主操作流，故仅保留其当前上下文板块；
- 把选定原型代码直接提升为生产实现：高保真录入原型是评审与交互验证用的自包含 HTML，生产实现必须重写但遵循其行为、结构与视觉意图，不复制其技术代码，也不把原型渲染结果作为生产交付物。

### D15 分层录入架构：新建向导 + 快速记录 + 就近入口

**选择**：数据录入采用分层入口，避免单个超大表单。全局「新建搬迁项目」采用四步向导（基本信息 → 搬迁范围 → 执行准备 → 确认方式），把项目级初始信息分步呈现；确认方式步骤展示录入摘要并支持保存为待进单、正式进单、未进单先执行三个确认路径；向导录入单号时自动创建对应开单记录（工程师必填、开单日期默认当天、备注可空）。当前选中项目通过「快速记录」抽屉（Drawer）按业务动作分别打开搬迁批次（批次与物流费用合并为一次记录，含费用登记日期、合同预算价与物流成交价）、搬迁仪器、上门活动、开单记录、验收报告、掉票、Ship-to 申请、损坏/维修事项、补齐进单核心资料等九类表单（二维码申请与序列号地址更新为独立模块，不进快速记录）；高优先项目队列行「记录」、当前上下文、详情 tab 标题栏均提供就近入口。**上门活动在同一页面记录拆机事实（拆机状态及拆机开始/完成日期）与各工作类型状态/日期**（TBD-05）。**项目主状态可人工选择，但提交时调用 lifecycle 校验并就地反馈**（D4，如取消约束、金额闭环）；**合同金额为 0 时的维修限制（TBD-15）在损坏/维修表单就地反馈**。**报表支持 Excel（.xlsx）、PNG、PDF 导出并就地反馈**。表单层只定义入口、字段呈现、校验反馈与提交后的展示同步；业务状态与金额校验等规则仍归对应业务能力，经 D4 校验入口消费，interface 不重复业务规则。

**理由**：负责人日常动作是"先处理项目提醒、再按项目连续记录事实"，分层录入使每次录入只面对该动作所需字段；就近入口让录入点贴近阅读位置；四步向导避免项目级初始信息的长表单；上门同页记录拆机与各工作类型状态/时间减少来回切换（TBD-05）；人工状态与就地反馈让负责人即时了解校验结果。

**被拒替代**：
- 单一巨型通用表单承担全部录入：字段过多、认知负担高且难以按动作校验；
- 所有录入必须进入固定入口（仅全局新建或仅详情表单）：增加操作路径，不符合"提醒直达、就近录入"的连续操作流；
- 拆机在独立子页面维护：与 TBD-05"同一上门活动页面记录"冲突；
- 在 interface 内重复实现业务状态与金额校验：与 D4 所有权冲突，导致口径分叉、双份实现。

### D16 视觉与可用性基线

**选择**：工作台采用专业、克制、高密度的企业运营视觉风格（客户已确认，非 TBD）：正文默认字号不小于 14px、表格正文不小于 14px、辅助文字原则上不小于 12px（低于 12px 仅限纯装饰性角标并保持清晰可辨）；标题、正文、辅助文字与状态色具备清晰层级与足够对比，多行文本以可读行高呈现；表单控件提供必填/可后补标识、字段帮助、校验失败就地提示、禁用/提交中状态、成功 Toast 与空状态；Modal/Drawer/Toast 支持打开时焦点移至首字段、Escape 关闭、label 关联可访问名称、仅点击遮罩空白处关闭；1024px 桌面视口下不发生页面级横向溢出（必要宽表格在自身区域内内部滚动），1440px 为主布局基准。本决策只定可验收的可用性与视觉基线，不规定具体框架、组件库或像素级实现；高保真原型 `prototype/relocation-workbench/selected/relocation-workbench-selected.html` 提供行为与视觉意图，生产实现必须重写但符合该意图，不复制原型技术代码。

**理由**：客户明确要求提升录入方式、字体可读性、视觉层级、表单与整体美化质量；明确字号、层级与表单反馈基线使首版界面可验收、可测试，避免"好看但不可测"；1024/1440 视口约束保证高密度工作台在常见办公桌面下仍可操作。

**被拒替代**：不设可验收的视觉基线、完全交由 apply 阶段临场决定（客户已确认方向，不应重新开放）；逐像素复制原型标记/样式/脚本作为生产代码（原型不是生产实现）；引入第三方 UI 框架或设计系统（属技术栈决策，留给 apply 前决策，不在本 change 选定）。

### D17 本地 SQLite 持久化

**选择**：应用作为 Windows 桌面应用（Electron + React + TypeScript）运行，全部业务数据持久化在应用本机的 SQLite 数据库中；数据库位于本地数据目录（tasks 0.2 已确定 userData/data 目录，访问库使用 Node 内置 node:sqlite，迁移机制使用 PRAGMA user_version，启用 WAL/foreign_keys/busy timeout）。领域层以 D1 稳定内部 ID、D4 状态校验入口与事实记录为存储模型，不依赖远程数据库或云服务；关闭并重新打开应用后数据保留。数据结构升级通过 schema 迁移执行，迁移失败时保留可恢复状态、不静默丢弃或损坏现有数据。本地应用账号（D12）仅是应用访问门槛，不加密 SQLite 数据库文件；数据库文件与备份的主要保护边界为 Windows 操作系统账户，登录本地账号不构成对直接读取数据库文件的防护。本决策基于已确认的运行与持久化边界（TBD-16 已解决，ADR docs/adr/0001-windows-desktop-local-sqlite.md），对应 local-data-persistence 能力。

**理由**：仅个人使用的单机边界下，本地 SQLite 提供事务性、可备份的单文件持久化，运维与备份最简单，不引入网络依赖；node:sqlite 为 Node 内置同步 SQLite 驱动，无原生依赖（与"不引入原生密码依赖"同一约束方向）；关闭重开保留与迁移保护保证数据连续性；账号仅作访问门槛、不加密数据库，避免误称登录即保护数据文件，数据文件与备份的保护责任由 Windows 操作系统账户承担。

**被拒替代**：远程数据库/云数据库（与已确认边界冲突，增加运维与网络依赖）；服务端进程或外部服务（超出单机桌面边界）；内存或文件快照持久化（无法保证事务性与一致性）；数据库加密与备份加密（超出已确认边界，本地账号不加密 SQLite，见 Non-Goals）。

### D18 本地备份：每日自动 7 份 + 手动备份/恢复

**选择**：应用在每日首次使用时，若当天尚无自动备份，则创建一份自动备份；自动备份仅保留最近 7 份，更旧的自动备份被清理，手动备份不受该数量限制。负责人可随时将数据手动备份到所选本地目录；可从所选本地备份恢复，恢复前要求确认并验证备份可读（在线 backup + integrity_check + 原子恢复），恢复失败不得覆盖当前数据；备份或恢复失败时给出明确错误、不静默视为成功；恢复操作前可做安全快照。备份内容为本地 SQLite 数据及其必要附属数据的可恢复副本（具体格式、文件命名与位置见 Open Questions）。

**理由**：单机数据的保护依赖本地备份；每日自动备份 + 最近 7 份轮转在恢复窗口与磁盘占用间取得平衡；手动备份覆盖立即与重大变更场景；恢复前验证（integrity_check）与失败保护避免"恢复即破坏"；明确失败反馈支撑负责人及时处置。

**被拒替代**：云备份/云同步（与已确认边界冲突）；只备份不做恢复验证（恢复路径不可信）；无轮转无限保留（磁盘占用不可控）；仅靠系统文件拷贝无版本化（无法满足最近 7 份轮转与恢复确认要求）。

### D19 导入能力边界：historical-data-import（领域语义）与 history-import-wizard（向导体验）

**选择**：本 change 同时新增两个导入相关能力。`historical-data-import` 拥有七类数据的规范化、ECC 聚合、校验、冲突处理、摘要封存、幂等、人工修改保护、全局原子提交与迁移审计语义（D11/D20~D27）；`history-import-wizard` 拥有数据管理入口、模板/文件/粘贴、列映射、分步目标网格、问题定位、草稿恢复、最终确认及大数据与键盘可用性体验（D28）。领域内核与向导界面按 D2 逻辑接缝分离：向导只消费领域校验结果与提交编排，不重复业务规则。

**理由**：领域语义与界面体验分离，使每份 spec 有明确实现归属、可独立测试，也避免向导界面直接耦合导入内核细节。

**被拒替代**：把向导体验全部并入 historical-data-import（规格过大、界面验收难以独立）；把领域语义全部并入 history-import-wizard（业务规则与体验混在一起，违背 D2 模块边界）。

### D20 采用"草稿工作区 + 正式业务库"双存储边界

**选择**：导入草稿保存在 app-private 的独立工作区数据库，不写入正式业务库的业务表。工作区保存：草稿、创建账号、最后修订、步骤与状态；输入来源、sheet、物理行、稳定源行 ID 与原始输入摘要；规范化单元格值、列映射、用户修正与冲突决定；局部/完整校验问题、进度与最后一次校验封存；解析任务的可恢复检查点。草稿状态机使用 `draft → parsing → needs_review ↔ validating → sealed → committing → succeeded`，另有 `cancelled`；`parsing`、`validating` 与 `committing` 为运行态，应用重启时前两者回到最后稳定草稿修订，`committing` 必须先核对正式成功审计再判定为 `succeeded` 或回到需重新校验状态。成功或取消后清除工作区中的原始值与规范化行，只在正式业务库长期保留必要摘要、数量与运行审计；异常遗留草稿按明确保留策略清理，删除前允许用户查看摘要。

**理由**：草稿与正式数据物理隔离，避免草稿被业务查询、备份或恢复流程误消费，也缩小长期敏感数据面；正式业务表只存已提交事实。

**被拒替代**：在正式业务库增加 staging 表——事务与备份虽然更简单，但草稿容易被业务查询或备份恢复流程误消费，且扩大敏感数据面。

### D21 文件、模板与粘贴共用版本化规范化管线

**选择**：所有输入先转换为统一的七类 `NormalizedRow` 概念结构，再进入领域映射与校验规则。当前模板使用一个工作簿，包含填写说明与七个业务 sheet，每个业务 sheet 包含模板版本与稳定 `source_row_id` 列。文件来源保留文件摘要、sheet 与物理行；粘贴来源保留草稿 ID、类别与粘贴批次行号。自动映射只接受当前模板字段及冻结别名，不做相似名称模糊匹配；旧五份来源工作簿继续通过冻结映射规则识别，未知 sheet 或列必须由用户明确归类、映射或排除。金额先转十进制字符串再进入领域层整数分值（D7）；ECC、服务单号、Account ID 与序列号始终按文本处理以保留前导零；Excel serial 按工作簿 1900/1904 日期系统解释，纯日期保留为业务日期，日期时间按升级时本机业务时区转换为业务日期（yyyy-mm-dd）后规范化，绝不使用导入时间补值。原始输入摘要按文件字节或规范化粘贴矩形计算；计划摘要对七类规范化记录、来源身份与冲突决定做稳定排序后计算，使语义相同的文件与粘贴得到同一计划摘要。

**理由**：单管线保证文件与粘贴在日期、空值与幂等行为上完全一致，避免双管线产生行为分叉。

**被拒替代**：文件走旧引擎、粘贴另写网格转换器——两套管线会在日期、空值与幂等行为上分叉。

### D22 Excel 在主进程受控读取，重处理放入工作线程

**选择**：文件选择与模板保存由主进程发起，renderer 只收到来源元数据、分页网格数据与问题摘要，不获得任意文件系统路径访问。Excel ZIP 结构先做有界预检，再在工作线程读取与规范化，避免阻塞 Electron 主线程或 renderer。初始资源边界集中配置并在界面公布：最多 20 个文件、单文件 100 MiB、压缩输入合计 250 MiB、展开合计 1 GiB、100 个 sheet、单 sheet 200 列、单网格至少支持 100,000 行且总行数上限 500,000。ZIP 预检必须使用直接声明的有界读取依赖，检查 entry 数、声明大小、实际展开总量与路径，不得依赖 Excel 解析库碰巧拒绝压缩炸弹。宏、公式、DDE 与外部链接不执行也不联网；公式仅在存在可信静态缓存值且目标字段允许时读取，否则成为字段错误；解析器不得把完整业务值写入日志或崩溃遥测。

**理由**：renderer 直接读取完整 workbook 的内存占用、文件权限与不受信内容边界都不适合桌面主操作界面。

**被拒替代**：renderer 直接读取完整 workbook。

### D23 草稿通过修订号与分页 API 读写

**选择**：renderer 不持有整份大草稿。IPC 使用草稿 ID、期望修订号、类别、行窗口与变更集：查询按范围、业务键、ECC 或问题筛选返回分页/窗口数据；文件解析与大粘贴按有界块写入工作区；网格编辑提交稀疏 cell patch，以修订号做乐观并发检查；自动保存成功后返回新修订号，冲突时要求刷新而非覆盖；解析、完整校验与提交使用 operation ID，支持进度订阅、取消与重复请求去重。大网格只渲染可见窗口及缓冲行；行号、ECC/业务键与问题列冻结。局部编辑只重校验受影响记录与 ECC，跨类唯一性、目标冲突与金额对账在完整校验阶段统一执行。

**理由**：一次 IPC 传输全部行并由 React 保存全量状态在 50,000–100,000 行时会造成结构化克隆、内存与渲染停顿。

**被拒替代**：一次 IPC 传输全部行并由 React 保存全量状态。

### D24 校验输出统一为可定位问题模型

**选择**：领域校验返回 `error | conflict | warning`，并携带类别、规范化记录键、目标字段、网格行、ECC/业务键、来源位置与稳定问题代码。向导将同一问题模型投影到单元格、行、步骤与全局问题面板。冲突解决只允许：选择一个合法来源候选、在允许字段上输入修正值、修正业务键/关联或排除明确不属于七类范围的来源；它不能绕过唯一性、金额、状态或引用不变量。"忽略全部错误"不进入命令模型。

**理由**：同一问题模型在单元格、行、步骤与问题面板间投影，保证定位与修正体验与领域校验结果一致，不产生口径分叉。

**被拒替代**：领域返回散落的字符串报告、界面另行解释——定位信息丢失且校验口径分叉。

### D25 校验封存绑定计划、规则与目标修订

**选择**：完整校验成功后生成 validation seal：`planDigest + templateVersion + mappingVersion + validationVersion + conflictDecisionDigest + targetSchemaVersion + targetBusinessRevision`。正式业务库新增单调递增的业务修订值，并由相关业务表的数据库触发器维护，使 facade、迁移写入与直接仓储写入都不能漏记。完整校验读取目标快照及修订；任何草稿修改、规则升级、schema 升级或目标业务写入都会使旧 seal 无效。提交时在正式写事务内再次比较 seal 与当前修订，并重新检查唯一键、引用与目标快照，不依赖 UI 禁用状态防止校验与提交之间的数据竞争。

**理由**：只保存计划摘要无法发现校验后有人新增相同 ECC、服务单号或修改迁移目标，存在"校验后数据变化仍提交"的时间差风险。

**被拒替代**：只保存计划摘要。

### D26 最终提交使用一个正式业务事务

**选择**：正式提交按以下顺序执行：1) 验证登录会话、受信 sender、草稿修订与 operation ID；2) 在事务外确认七类状态完整、seal 存在，并创建与验证导入前安全快照；3) 获取唯一提交互斥锁并开始正式业务库的立即写事务；4) 在事务内复核 schema、业务修订、计划摘要、唯一性、引用与目标快照；5) 按依赖顺序写项目/合同，再写六类子记录，所有 writer 接收同一事务连接、禁止内部提交；6) 写来源审计、目标快照、登录账号 ID/用户名快照与成功运行审计；7) 对七类计划数、新增数、修正数、幂等跳过数与实际目标数做写后对账；8) 对账成功后一次提交，任何异常整体回滚。提交期间草稿锁定；operation ID 与 seal 唯一约束防止双击或重复 IPC 产生第二次并发提交；应用在事务中退出时依赖数据库事务回滚，重启后以成功审计与 seal 唯一记录判定结果、不能自动重提。

**理由**：按 ECC 批次提交允许前一项目成功、后一项目失败，不符合用户选择的七类一次原子导入；单事务使任意类别、审计或对账失败都不会留下部分结果。

**被拒替代**：保留按 ECC 批次提交并在 UI 汇总。

### D27 迁移运行归属登录账号，业务事实保持历史来源

**选择**：所有向导 IPC 复用现有 authenticated + trusted sender 守卫（D12）。草稿记录创建账号，最终运行审计记录提交账号内部 ID 与提交时用户名快照；重新登录继续草稿后，原创建人不被重写，最终提交人按实际账号记录。业务 writer 继续把生成记录标记为 `history_import`（见 1.5 来源标记）。迁移运行审计用于回答"谁确认并执行了导入"，但不把七类历史事实标记为该账号手工录入，也不进入手工工作量统计。

**理由**：在保留"迁移数据不计手工录入"语义的同时，让向导内导入具备可追溯的确认账号（TBD-18/21 已确认事实归属边界）。

**被拒替代**：向导导入不记录账号（无法回答谁确认执行了导入）；把导入事实计入提交账号工作量（与历史来源语义冲突）。

### D28 向导沿用工作台设计系统但采用全窗口工作区

**选择**：入口放在"数据管理"，与手动备份和恢复并列。导入网格需要稳定高度、冻结列与问题侧栏，因此使用全窗口工作区而非 modal：顶部保留返回工作台、标题、当前账号与草稿保存状态；左侧为七步状态，中部为工具栏与目标网格，右侧为可收起问题面板；底部固定上一步、保存并退出、下一步，最终步骤才显示"确认导入"；沿用深绿导航、浅灰背景、白色工作面板与现有字号/对比基线（D16）；错误、冲突与警告同时使用文字、图标与颜色；异步通知不抢夺网格焦点。交互结构以 history-import-wizard 规格为准，不把通用工作台队列或项目上下文复制进导入工作区。

**理由**：七步流程与大数据网格需要独立全窗口空间，同时保持工作台数据管理导航意图与视觉基线。

**被拒替代**：使用 modal 承载导入流程（空间不足、网格无法虚拟化）。

### D29 CLI 在向导达到行为等价后一次移除

**选择**：现有解析、映射与领域校验模块先从 CLI 编排中解耦并由向导调用。只有模板/文件/粘贴、完整校验、全局原子提交、幂等与审计测试全部通过后，才删除 `migrate-cli.ts`、CLI adapter、`migrate:build`/`migrate:dry-run` scripts 及外部操作文档；删除时保留合成数据测试夹具，不把真实 docs 文件纳入自动测试。不保留隐藏 CLI 作为备用路径；运维恢复依赖现有备份/恢复能力（D18），而不是绕过向导的第二导入通道。

**理由**：向导达到行为等价前保留内核测试基线可降低切换风险；一旦向导成为唯一入口，隐藏 CLI 会绕过 UI 守卫与审计，必须整体移除。

**被拒替代**：保留隐藏 CLI 作为备用路径。

### D30 时间口径：业务日期与审计时间分离

**选择**：业务时间与审计/技术时间分开记录（已确认，2026-08-09）：

- **所有业务时间仅记录业务日期 yyyy-mm-dd**（不含时分秒与时区偏移）：进单日期、开单日期、掉票日期、撤销日期、取消日期、费用登记日期、备件申请日期、登记日期、更新日期（序列号地址更新）、申请日期（二维码申请）、首次提交日期、完成日期（Ship-to 申请）、到访日期、工作事实开始/完成日期、计划上门/运输日期、实际装机完成日期、提醒日期等业务字段一律以业务日期表达。
- **审计/技术时间保留精确 ISO**（含时区偏移）：系统创建时间、动作记录时间、导入运行时间、记录最后修改时间、迁移运行审计中的运行与提交时间等只用于审计或技术追溯，不参与业务归属与报表月份归属。
- **历史值按升级时本机业务时区转换为日期**：历史数据导入或既有数据升级时，源日期时间按升级时本机业务时区转换为业务日期（yyyy-mm-dd）后写入业务字段；导入运行时间仅进审计，绝不替代源业务日期。
- **报表/月度归属按业务日期**：进单金额、掉票金额与次数、开单量、损坏维修、物流费用、Ship-to 申请、二维码申请、序列号地址更新等所有时间归属均以对应业务日期所属月份计算。
- **界面使用日期控件**：工作台录入与筛选界面为业务日期字段提供日期控件（yyyy-mm-dd），不使用自由文本或时间选择器录入业务时间。

**理由**：业务记录与统计只关心"发生在哪一天"（月度归属、提醒到期分类、合同起止等均为日粒度），记录时分秒与时区偏移既增加录入与展示复杂度，又会因时区解释产生口径分歧；审计/技术时间仍以精确 ISO 保留，保证可追溯性与时区无关；历史值按升级时本机业务时区一次性转换为业务日期，避免跨时区重放与重复换算；日期控件保证录入格式一致。

**被拒替代**：业务字段保存带偏移 ISO 时间并允许任意时区（业务口径与展示随解释时区漂移、月度归属出现跨日歧义，已被本次确认规则取代）；业务时间仅存 yyyy-mm 月份（丢失日粒度，无法支持提醒到期分类、合同起止与精确归属）；删除全部时间信息（审计与技术时间仍需保留精确 ISO）。

## Risks / Trade-offs

- **R1（本地数据风险）本机敏感数据与单点故障**：业务数据仅存于单台 Windows 机器的本机 SQLite，存在本地敏感数据暴露、文件损坏、备份失效与安装升级影响数据的风险。→ 本地应用账号仅作为访问门槛（D12），本机数据文件与备份的主要保护边界为 Windows 操作系统账户；每日自动备份仅保留最近 7 份 + 手动备份（D18）；备份/恢复失败明确报错且恢复失败不覆盖当前数据；恢复操作前可做安全快照；Windows 安装包与升级流程纳入交付文档与验收；交付文档明确"登录本地账号不能防止直接读取数据库文件"。
- **R2 手工数据质量**：全部外部事实（经理批复、工程师执行、合同金额、区域等）由负责人手工录入，存在录入错误与口径漂移；区域为手工文本 trim 后精确分组（TBD-12），文本变体可能静默拆分分组。→ 在业务允许处做低成本校验（金额有值必须 > 0、仅合同金额允许 0、必填原因、业务键唯一、客户名称 trim 后唯一），按业务规则以警告而非阻断呈现；区域统一 trim 与单一维护点，报表下钻可查看组内明细以暴露分组异常。
- **R3 历史数据无法拆分或必填缺失**：一个 ECC 对应多条执行记录等源数据无法明确拆分映射，或目标必填字段（含 ECC、费用登记日期）缺失，或不同源记录服务单号重复。→ 以 ECC 聚合主键导入全部执行数据；重复服务单号进入冲突清单、解决前禁止提交（TBD-21）；无法明确拆分的来源进入冲突清单由负责人确认，不按文本推断；向导对目标必填缺失输出类别、目标字段、网格行与来源位置，用户在向导内修正后重新完整校验，正式提交前不得存在错误、任一错误或未解决冲突则整体不可提交；历史批次缺费用视为异常数据、不提供独立补录入口；目标可选字段允许为空、不用导入时间替代；状态重建确定性执行，不产生猜测状态。
- **R4 实时报表的一致性/性能**：报表对事实全量实时计算；事后编辑会改变历史统计——该变化由已确认规则（掉票直接覆盖编辑与撤销终态、取消排除收入/掉票指标，TBD-10/19；区域手工文本实时重算 TBD-12）共同导致，而非缺陷——但查询成本随数据量增长，且无法复现"某一历史时点"的报表快照。→ 单负责人、项目级聚合计算的量级下可行；如规模增长，索引/缓存优化属 apply 前决策；报表快照为已确认 Non-goal，不复现历史时点属已接受取舍。
- **R5 掉票直接编辑缺乏历史版本**：掉票"直接覆盖、不保留旧值，只记最后修改时间"，无法审计旧值；撤销后终态无法回退。→ 按确认规则实现撤销（记录时间与原因）且撤销后为终态，更正新增有效掉票；保留最后修改时间；将"无历史版本"作为已接受业务取舍在评审中向业务方明示。
- **R6 人工状态调整与自动触发的冲突风险**：负责人人工调整主状态与 TBD-07 实际装机自动待验收、验收自动待掉票、金额闭环自动重算可能冲突。→ 由 D4 单一校验入口统一处理：自动触发优先，人工调整在校验入口内校验合法状态与取消/金额约束后落库；workbench-interface 提交前就地反馈，避免静默冲突。
- **R7 模块化单体边界的可调整成本**：边界是逻辑接缝，apply 阶段按实现便利调整会带来改动成本。→ 以稳定内部 ID 与领域内核降低模块耦合；调整限于模块内部实现，对 spec 定义的外部行为无影响。
- **R8（长事务）七类全局原子提交比按 ECC 提交持锁更久** → 所有解析、规范化和大部分校验在工作区完成；正式事务只做 revision 复核、写入和对账（D26）。
- **R9（校验失效误判）业务修订触发器可能遗漏相关表或因无关写入频繁使 seal 失效** → 明确维护相关表清单并做 schema 迁移测试；允许保守失效，不允许漏报（D25）。
- **R10（草稿敏感数据）可恢复草稿复制了客户与业务数据** → app-private 存储、Windows 账户边界、最小日志、成功/取消清理与可见保留策略；不宣称登录账号能加密文件（D20）。
- **R11（Excel 资源攻击）解析器可能在检查前耗尽内存或展开恶意 ZIP** → ZIP 中央目录与展开量预检、硬上限、工作线程与可取消的分块处理（D22）。
- **R12（大网格复杂度）100,000 行编辑、撤销与问题定位会显著增加 UI 状态复杂度** → disk-backed 草稿、窗口查询、稀疏 patch 与受影响范围校验；不把完整数据集放进 renderer 状态（D23）。
- **R13（通用编辑器膨胀）任意列映射与表格编辑容易演变为 ETL 产品** → 目标字段固定、别名冻结、冲突动作受限，不支持表达式和用户自定义 schema（D24）。
- **R14（真实数据仍不可导入）向导上线不代表 554 个错误与 124 个冲突自动消失** → 保留全部领域门禁，使用真实只读验收核对定位能力，禁止用默认值消除错误数。
- **R15（移除 CLI 的回退成本）向导故障时不再有第二执行入口** → 移除前要求行为等价与打包 Electron E2E；故障只允许升级修复或备份恢复，不保留未经 UI 守卫的旁路（D29）。

## Migration Plan

存量数据一次性导入（对应 historical-data-import 与 history-import-wizard 能力），实施阶段与 D11/D19~D29 一致：

1. **建立持久化边界**：新增草稿工作区 schema、正式业务修订与迁移运行审计 schema、版本迁移与清理策略；先保持无用户入口（D20/D25）。
2. **抽离统一内核**：把模板、文件、粘贴转换为统一规范化管线，保留现有映射、校验、来源审计与目标快照规则（D21）。
3. **改造提交编排**：移除 writer 内部分批提交，增加 seal、提交互斥、安全快照、单事务写入与逐类对账（D25/D26）。
4. **接入受保护应用通道**：增加分块 IPC、进度/取消、草稿修订与 facade 编排，全部经过登录会话与 trusted sender 守卫（D23/D27）。
5. **交付全窗口向导**：按七步实现模板、文件、粘贴、列映射、ECC 中心、虚拟网格、问题面板、草稿恢复与最终确认（D28）。
6. **移除旧执行面**：完成行为等价验证后删除 CLI 入口、构建脚本与旧文档，更新部署与用户说明（D29）。
7. **验收与发布**：用合成七类数据做故障注入、幂等、人工修改保护、50,000 行输入与 100,000 行网格测试；对真实 docs 仅执行向导预检并核对源文件哈希，不在错误/冲突清零前提交。

**时间口径（关键约束）**：所有业务时间仅记录业务日期 yyyy-mm-dd，审计/技术时间保留精确 ISO（见 D30）。导入/系统记录时间只作为审计时间保存；源业务日期（掉票日期、开单日期、实际物流费用申请/登记日期、进单确认日期等）一律映射到对应业务字段并按升级时本机业务时区转换为业务日期；目标必填的源业务日期缺失由校验报错且该记录不可提交，目标可选的源业务日期缺失则保留为空、**绝不**用导入时间填充（TBD-18）。项目状态由导入事实确定性重建，迁移数据不视为负责人手工录入、不计入确认账号的手工工作量。

**回滚**：校验阶段不写业务数据、天然可弃；正式提交为单事务，任一失败整体回滚、不产生部分数据；提交前创建并验证导入前安全快照；已提交错误通过受保护的 forward-fix 修正，不通过回退版本或恢复旧库覆盖之后的人工业务修改。

**部署说明**：历史数据导入由已登录负责人通过工作台内"数据管理"向导执行，不新增管理员账号/角色；移除外部迁移 CLI、`migrate:build`/`migrate:dry-run` 构建命令及对应文档，向导成为唯一导入入口；导入草稿与业务数据均在 Windows 操作系统账户保护边界内（D12/D17）。

## Open Questions

以下为**不改变当前 spec 与任务拆分**的后置技术问题，可留待 apply 前决定；业务性 TBD 已全部确认，不在此重新开放。

- Electron 具体版本、打包器与 Windows 安装包形态（含升级与自动更新策略）——已确认 Electron + React + TypeScript 方向并选定 Electron 43.3.0、Forge 7.11.2 + webpack-typescript + React（D17/ADR/tasks 0.2），打包细节 apply 前确定。
- SQLite 访问库与 schema 迁移工具选型——已确认本地 SQLite 并选定 node:sqlite + PRAGMA user_version（D17/tasks 0.2），具体迁移脚本组织 apply 前确定。
- 本地数据目录位置、备份文件格式/命名与保留位置——D17/D18 只定了行为边界（userData/data、在线 backup + integrity_check + 原子恢复、安全快照），实现细节 apply 前决策。
- 本地账号数据（用户名、scrypt 派生值与随机盐、一次性恢复码派生值）的存放位置与账号初始化/恢复码生命周期实现细节——D12 已定安全存储方式（Node 内置 scrypt + 每条记录随机盐 + timingSafeEqual、无原生密码依赖、恢复码只展示一次、使用后失效并重新生成），具体存放位置与 scrypt 参数 apply 前决策；账号数据同样不加密存储，其保护边界为 Windows 操作系统账户。
- 恢复操作前是否需要额外安全快照（恢复前快照策略）——D18 已定"恢复失败不覆盖当前数据"，是否追加恢复前快照 apply 前决策。
- 金额定点类型的物理表示（已定分为整数）、索引策略——apply 前决策。
- Excel（.xlsx）/PNG/PDF 导出技术库选型——TBD-17 已定导出格式与"导出当前筛选实时结果"，具体技术库留 apply 时选择。
- 日期/时间的物理表示与时区处理（已定：业务时间仅记录业务日期 yyyy-mm-dd，审计/技术时间保留精确 ISO，历史导入值按升级时本机业务时区转换，见 D30）——业务日期字段口径已由 spec 定义，物理表示后置。
- 报表下钻的交互深度与图表呈现形式——不影响指标口径（口径以 spec 为准）。
- 附件/文件存储：已确认不存储验收报告附件或外部链接（业务 Non-goal）；不据此排除其他文件/附件场景，若后续引入再行决策。
