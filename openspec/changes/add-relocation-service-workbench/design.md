## Goals / Non-Goals

**Goals:**

- 提供可支撑 14 个能力规格的逻辑架构：模块化单体逻辑边界（与 14 个 capability 一致、可调整）、聚合边界与关系、稳定内部 ID 与业务 ID 分离。
- 以“事实记录 + 集中状态推导”为统一机制，使项目主状态、标准待办完成判定、报表指标都从同一事实集推导，避免各模块各自维护状态导致不一致。
- 让金额精度、掉票重算、Ship-to 不可变、迁移幂等/冲突/事务等关键规则有明确、可定位的实现归属，且 20 项未决暂定决定可在不推倒架构的前提下被修订。
- 使一次性存量迁移具备可验证、可回退的阶段流程（冻结映射 → dry-run → 冲突确认 → 事务导入 → 对账 → 切换）。
- 使本地数据具备可验证的持久化、备份与恢复路径（本地 SQLite、每日自动 7 份备份、手动备份/恢复与失败保护）。

**Non-Goals:**

- 不决定具体版本、打包器、ORM、SQLite 访问/迁移库、数据目录等实现细节（属于 apply 前决策，见 Open Questions）。
- 不引入微服务、通用工作流/规则引擎、事件溯源、远程数据库、云同步或外部集成框架。
- 不做数据库加密、应用密码或云备份（超出已确认边界，见 D17/D18）。
- 不做任何代码实现。
- 不重述业务范围、领域规则与能力内容（分别见 proposal.md 与后续 specs）；不把未决暂定决定当作最终业务结论（见 D13）。

## Decisions

每项决策给出选择、理由与被拒替代方案。除特别说明外，业务判定均引用 proposal.md《暂定决定》，本设计只承担其技术/逻辑含义。

### D1 稳定内部 ID 与业务 ID 分离

**选择**：每个聚合/实体由系统分配一个创建时生成、永不复用、不随业务变更的稳定内部 ID，作为全部引用与关联的键；ECC、服务单号、Ship-to 的 Account ID、仪器序列号、客户编号等业务 ID 作为独立字段保存，各自带可空与唯一性约束。

**理由**：业务 ID 的特征彼此冲突且与“引用稳定”冲突——ECC 在正式进单后才具备（TBD-01，待进单阶段仅临时编号）；服务单号要求全局唯一但迁移数据存在重复（TBD-21）；Ship-to 创建后不可修改（已确认）；序列号在项目内唯一、跨项目可重复（TBD-02）。内部 ID 与业务 ID 分离后，补 ECC、迁移纠错、撤销与状态重算都不会破坏既有引用。

**被拒替代**：以业务 ID 直接作主键（无法表达无 ECC 的待进单态，迁移冲突会使建库失败）；正式进单时把临时编号“升级”为 ECC（改变标识符、破坏既有引用）。

### D2 模块化单体逻辑边界（与 14 个 capability 一致）

**选择**：一个逻辑单体，内部按能力划分为模块，与 14 个 capability 一一对应；模块间通过进程内服务调用协作，共享一个领域内核（金额值对象、ID 规则、状态推导入口）。该边界是**逻辑接缝**而非独立部署或独立存储；apply 阶段可按实现便利调整，但不改变 14 个能力的外部行为与 spec 定义。

**理由**：单角色、小团队、无外部集成的规模下，单体是最简单直接的形态；边界与 14 份 spec 对齐，使每份 spec 有明确实现归属，可独立构建与测试，也为后续 tasks 提供拆分依据。

**被拒替代**：微服务（无独立扩展、独立团队或独立故障域需求，只增加运维与分布成本）；事件总线/事件源（proposal 明确排除事件溯源，且状态规则是封闭有限集，事件总线只增加间接性）；通用工作流/规则引擎（规则封闭有限，引擎引入额外抽象与学习成本，与 Non-goals 冲突）。

### D3 聚合边界与跨聚合关系

**选择**：

- **搬迁项目**为项目级聚合根；**合同**是该项目聚合内与项目 1:1 的独立领域对象（持有临时编号、正式 ECC、合同 USD 含税金额与进单金额快照、最终可确认金额、正式合同变更记录），作为独立对象建模、不折叠为聚合根上的平铺字段；搬迁项目聚合根持有所属区域、未进单先执行标签、取消信息（不可恢复）、项目默认地址；项目聚合维护项目级不变量（正式进单必要条件、最终可确认金额 ≥ 累计掉票金额、录入金额有值必须 > 0）。
- 以下为独立聚合，跨聚合引用一律使用稳定内部 ID（D1）：搬迁批次（计划运输日期、运输公司、人民币原价/折后价报价层）、物流费用记录（登记日期、预算/成交/物流费用人民币）、搬迁仪器（序列号、所属批次、目的 Ship-to、二维码手工标记）、上门活动（含“活动 × 仪器 × 工作类型”事实行，见 D5）、开单记录、Ship-to 申请（仅记录客户与新址地址，不关联仪器、不保存地址快照）、Ship-to（不可变主数据）、损坏/维修事项（聚合其下单个备件的备件号/数量/金额与维修过程备注，不设独立备件申请）、序列号地址更新记录、二维码申请、掉票记录、客户主数据、自定义待办。
- 跨聚合不变量（如掉票累计与最终可确认金额的关系）不在各聚合内重复实现，由对应模块的领域服务在单一入口校验。

**理由**：一致性边界明确，避免“项目巨型聚合”使所有写操作互相锁定；事实 + 推导机制下，聚合保持“可独立变更的最小一致性单元”，与 14 个能力的模块划分对齐。

**被拒替代**：项目聚合包住全部子对象（所有变更锁定全项目、耦合过高）；所有对象完全独立无聚合（不变量无处归属、关系散乱、难以保证金额闭环）。

### D4 事实记录 + 集中状态推导

**选择**：把业务事件作为事实记录持久化（正式进单时间、首次上门活动开始、首个搬迁批次开始运输、实际装机完成时间、验收报告形成日期、掉票发生时间与金额、取消时间与原因、实际物流费用登记时间、首次提交时间、序列号地址更新等）；项目主状态、标准待办完成判定、报表指标均由**同一个推导入口**从事实集合计算，主状态不可直接编辑（TBD-09）；执行中→待验收由录入实际装机完成时间触发，计划装机时间不触发（TBD-07 已解决）。relocation-project-lifecycle 模块是主状态推导规则的唯一所有者；其他模块提供事实、消费推导结果，跨模块协作通过进程内直接服务调用完成。

**理由**：主状态由事实推导是暂定决定（TBD-09），待掉票/已完成按金额闭环重算是已确认规则（TBD-11 已解决），掉票编辑后重算属暂定（TBD-19）；单一推导入口保证状态、待办、报表口径一致。

**被拒替代**：持久化状态列并允许手工维护（与 TBD-09 冲突、易漂移、事后重算无依据）；各模块各自计算状态副本（规则重复、结果分叉）。

### D5 活动 × 仪器 × 工作类型

**选择**：上门活动记录事实（到访时间、参与工程师）；工作内容表达为“活动 × 仪器 × 工作类型”的事实行——同一活动的同一台仪器可含多种工作类型（拆机、装机、维修等），同一活动可处理多台仪器；工作事实采用两态持久化：不存在对应工作事实即表示未开始，创建事实时状态为进行中并记录开始时间，完成后状态为已完成并记录完成时间，“未开始”不作为持久化状态；仪器拆装进度由工作事实是否存在及其状态推导（事实不存在 = 未开始、进行中 = 进行中、已完成 = 已完成），不以仅存在工作事实记录即视为完成，不设可编辑的进度字段。活动×仪器工作事实行由 relocation-execution 拥有；维修上门活动同时关联损坏/维修事项，为多对多关系（TBD-24，该关联规则归属 damage-repair-tracking），并校验该事项所属仪器属于该活动的仪器集合。

**理由**：TBD-05 与 TBD-24——一次活动多类型、多仪器、可处理多事项；工作事实两态持久化并记录开始/完成时间，未开始由事实缺失表达，使拆装进度可推导、可随事实修正重算；维修工作与损坏事项解耦（事项独立于生命周期、不阻塞状态流转），同一事实模型同时支撑拆装进度与维修关联，避免维护两份执行记录。

**被拒替代**：上门活动单一工作类型字段（无法表达多类型、多仪器）；拆装进度作为可编辑字段（与推导机制冲突，无法从事实重算）；以仅存在工作事实记录即视为完成（记录存在但尚未完成时无法表达进行中，未开始也无法与进行中区分，与 TBD-05 两态语义冲突）。

### D6 不可变 Ship-to、项目默认地址与逐台地址更新

**选择**：Ship-to 为不可变主数据，以 Account ID 标识，创建后禁止更新（目的地址变化 = 申请新 Ship-to）。Ship-to 申请仅记录客户名称与新址地址，不关联搬迁仪器、不保存结构化地址快照；申请创建时 Account ID 可空，由系统外完成流程返回后由负责人补入全局唯一的 Account ID（补入后申请进入已完成并记录完成时间，申请完成前 Account ID 必填），补入的 Account ID 对应创建的不可变 Ship-to。搬迁项目设置项目默认地址，搬迁仪器默认沿用项目默认地址；实际仪器地址仅由序列号地址更新记录（serial-address-update 模块）逐台表达，该更新事实不修改 Ship-to 主数据。

**理由**：TBD-04——申请仅记录客户与新址地址，不关联仪器、不保存地址快照（客户确认）；Ship-to 不可变是已确认规则，保证历史引用与统计稳定；Account ID 完成前必填保证已完成申请必有对应不可变 Ship-to；项目默认地址 + 逐台更新事实避免每台仪器重复申请，序列号地址更新记录表达实际关联事实（客户确认）。

**被拒替代**：原地修改 Ship-to（违反已确认规则、破坏历史引用）；申请保存结构化地址快照或关联搬迁仪器（与客户确认规则冲突）；以项目默认地址直接作为所有仪器地址且不记录逐台更新（无法表达实际关联事实）。

### D7 金额十进制定点、精度、币种边界与固定汇率

**选择**：金额一律以十进制定点类型表达（逻辑类型、精确到分、两位小数，全程禁用二进制浮点）；舍入规则为四舍五入，且只在明确聚合点应用（避免逐级舍入放大）。合同金额与掉票/最终可确认金额以 USD 表达；物流分两层记账——批次报价层记录人民币原价与折后价，物流费用记录层记录登记日期、预算价格、成交价格与物流费用（人民币），不做 USD 折算，成交价格大于预算价格仅警告；备件金额仅 USD/RMB，RMB→USD 按固定常量 `1 USD = 7.2 RMB` 折算（配置常量，非汇率服务），USD 折算值用于统计口径。录入金额有值必须大于 0，不允许 0 或负数，无 0 金额闭环（TBD-11 已解决）；掉票单笔 > 0；最终可确认金额可下调但不得低于累计掉票金额（TBD-11 已解决）。

**理由**：TBD-11 已确认的精度、舍入与大于 0 约束，需求 8.3 的固定汇率；定点类型避免求和与占比的浮点漂移；保留原币可追溯、支持“仅 USD 与 RMB”的币种边界；物流人民币记账避免多币种折算歧义，报价层与费用层分开避免把成交价误作预计物流成本（客户确认）。

**被拒替代**：浮点（累计与占比精度漂移）；只存 USD 折算值（丢失原币金额，无法复核）；接入实时汇率（proposal 明确不做）；物流费用按 USD 折算（客户确认物流以人民币记账）；以成交价作为执行前预计物流成本（客户确认不采用该口径）。

### D8 掉票编辑/撤销与末端状态重算

**选择**：掉票记录按已确认规则允许直接覆盖日期与金额，系统自动记录最后修改时间（不保留旧值）；不允许物理删除，撤销通过记录撤销时间与原因的撤销动作实现，撤销后不计金额与次数。任何掉票编辑/撤销或最终可确认金额调整后，由 D4 的统一推导入口按“累计掉票金额 vs 最终可确认金额”在待掉票/已完成之间重算（录入金额有值必须 > 0、无 0 金额闭环），并同步重算相关报表聚合。新增掉票累计不得超出最终可确认金额，超限时先调整最终可确认金额并记录原因。取消规则（TBD-10 已解决）：任何无掉票历史（含撤销）的未取消主状态项目均可取消，取消不可恢复，取消必须记录取消时间与原因并保留已发生的上门活动、物流与费用记录；取消期间禁止修改合同金额、最终可确认金额与掉票记录。

**理由**：TBD-19/20——掉票“不物理删除、只撤销”属暂定决定，TBD-11 的闭环重算与大于 0 约束、TBD-10 的取消规则已确认；撤销动作保留时间与原因，使统计重算和审计链确定；取消不可恢复按客户确认结论实施。

**被拒替代**：物理删除（违反 TBD-19，删除后统计与状态无依据）；对每次编辑保留完整历史版本（proposal 明确“不保留旧值和更正原因，只记最后修改时间”，属已接受业务取舍，见 Risks R5）。

### D9 标准待办作为派生规则，单一规则所有者

**选择**：标准待办是派生视图而非可编辑实体：workbench-todos 模块是唯一规则所有者，持有 TBD-23 的封闭清单（七类标准待办），每类定义生成条件、完成条件与绑定的关键日期；标准待办在相应信息缺失时即生成，不要求先有排期；若存在计划上门/运输日期则绑定为关键日期，无日期时仍生成但不判逾期；标准待办按当前事实派生，只显示当前有效的标准待办、不保存完成历史；缺失条件持续满足不重复生成，条件消除后待办自动完成并从列表消失，后续再次缺失会重新出现；缺进单核心资料对所有处于待进单且核心资料缺失的项目生成，不仅限于未进单先执行项目。仪器"二维码是否申请"为手工标记，不自动生成任何标准待办。自定义待办是独立的用户管理记录（手工完成/取消）。临期/今日到期/已逾期的判定是该模块内的纯函数（默认临期范围 7 个自然日、可配置，需求 7.7）。

**理由**：TBD-23；单一规则所有者避免各能力模块各自生成待办导致规则重复与口径分叉；自动完成判定与 D4 推导机制天然一致，无需额外同步。

**被拒替代**：各模块各自维护待办规则（规则重复、口径分叉、完成判定依赖各模块自算状态）；通用任务/工作流引擎（超出需求，且与 Non-goals 冲突）。

### D10 实时派生报表

**选择**：报表（operational-reporting）按需实时从事实集合经同一推导函数计算，不建报表快照表；月份区间、区域、开单业务类型、运输公司等筛选与下钻在查询层对事实执行；导出仅 CSV（TBD-17）。指标口径字典以 spec 为准，实现归属 reporting 模块，读取的事实与推导入口与其他模块共享。

**理由**：TBD-17 要求实时；掉票编辑（已确认直接覆盖规则）、取消（TBD-10 已解决）等事后变更都会影响统计——历史报表变化由已确认规则与 TBD-12/17 暂定规则共同导致——实时推导天然反映最新事实，无需快照刷新；单负责人、项目级聚合计算的数据量下按需计算可行。

**被拒替代**：定时快照/物化报表表（TBD-17 暂定不做月结与报表快照，且掉票事后编辑会造成快照过期）；引入 BI 工具（外部集成，Non-goal）。

### D11 一次性迁移：dry-run、幂等、冲突、事务

**选择**：迁移是一次性动作，由**工作台外部的部署运维人员**执行，不新增管理员账号或角色、不进入工作台登录体系（无应用内登录，见 D12），按阶段执行：字段映射冻结（版本化映射配置）→ dry-run（只读执行，产出解析/冲突报告与目标必填字段缺失错误清单，不写数据）→ 冲突人工确认（不自动覆盖，负责人逐项确认）→ 事务导入（每个导入批次作为一个整体提交或整体回滚，批次内任一记录失败则整体回滚、不产生任何部分数据）→ 对账（记录数、金额合计、掉票累计、状态重建结果与源文件核对）→ 切换（日常操作与报表切换到新模型，源 Excel 降级为只读参考）。匹配策略优先业务键（ECC/服务单号/Account ID/序列号），否则用“源文件 + sheet + 行号”；无法明确拆分的旧数据保留未分批并进入冲突清单。幂等键为“（源文件、sheet、行号）+ 业务键”：已成功批次同源修复后重跑不重复写入。dry-run 对目标必填字段缺失（含物流费用记录登记日期）输出源文件、sheet、行与字段错误，客户修改源 Excel 或补录模板后重跑；正式导入前不得存在错误，批次内任一目标必填字段缺失/错误则整个批次不写入、不产生部分导入；正式事务导入，导入后不存在待补必填字段，不建补录 UI、不提供持续导入功能（TBD-18 已解决）。目标可选字段允许为空，缺失不构成错误。导入时间作为审计字段单独保存，**绝不**替代源业务时间：目标必填的源业务时间缺失由 dry-run 报错且该行不导入；目标可选的源业务时间缺失则保留为空、不用导入时间填充（TBD-18 已解决、验收场景 23）。

**理由**：TBD-18 已解决——多源 Excel 存在字段冲突、重复服务单号、无法拆分行、源业务时间缺失；dry-run 对必填缺失报源文件/sheet/行/字段、客户修改源 Excel/补录模板后重跑、正式导入前不得存在错误、批次内任一目标必填字段缺失/错误则整个批次不写入且不产生部分导入、正式事务导入、不建补录 UI；一次性 + 由工作台外部署运维人员执行的范围使 dry-run、幂等与事务成为可行且必要的保障；状态由导入事实经 D4 推导入口确定性重建，避免手工指定状态。

**被拒替代**：持续导入功能与补录 UI（proposal TBD-18 已解决 Non-goal，仅首版一次性迁移、不建补录 UI）；按文本相似度推断缺失字段（proposal 明确禁止推断）；无事务的逐行写入（部分失败会污染数据且难以修复）。

### D12 无应用内登录，依赖 Windows 操作系统账户；不集成外部系统

**选择**：应用不提供应用内登录、注册、密码或角色权限体系；启动后依赖 Windows 操作系统当前登录用户账户访问本机数据。不实现任何外部系统适配器与同步任务，不接入远程数据库或云同步（见 D17）。不设项目负责人字段。本决策基于已确认的运行与持久化边界（TBD-16 已解决），不再属暂定；具体打包、安装与数据目录等实现细节属 apply 前决策，不在本设计中选定。

**理由**：仅个人使用、单 Windows 桌面的边界下，应用内账号体系不提供额外价值；Windows 操作系统账户已提供本机访问边界；封闭边界使首版范围可控；D1 的稳定内部 ID 与 D2 的模块接缝为将来可能的集成预留了不破坏现有数据的挂载点。

**被拒替代**：应用内认证/权限体系（超出首版边界，Windows 账户已提供访问控制）；接入外部身份源、远程数据库或云同步（与已确认边界冲突）。

### D13 20 项未决暂定决定登记与按模块复核

**选择**：proposal.md《暂定决定》是未决暂定决定（TBD-01~25 中除已解决的 TBD-07/10/11/16/18 外）的登记源（含风险评级），本设计只引用、不改写；每项暂定决定在相关能力实现时按其风险等级处理。TBD-07/10/11/18 已由客户确认（2026-08-07），当前高风险未决 0，不再设置高风险评审门；剩余 20 项中/低风险暂定决定按所属模块在对应能力实现前复核确认（relocation-project-lifecycle 涉及的 01/08/09/12/25、project-financial-closure 涉及的 19/20、historical-data-import 涉及的其他待定项等）。暂定决定的修订只发生在 proposal 登记处，设计与规格随之局部更新，不推倒架构。TBD 与能力归属对照见附录 A。

**理由**：proposal《Impact》要求未决暂定项在对应能力实现层开始前按模块复核；已解决项按客户确认结论直接实施；暂定决定集中登记使修订影响可控、可追踪。

**被拒替代**：把未决暂定值当作最终业务结论直接实施（暂定项可能被推翻，返工与数据重建成本高）；因部分未确认而阻塞全部规划（与 proposal“使首版可实施”的目标矛盾）。

### D14 任务指挥台主结构 + 生命周期吞吐 + 当前上下文

**选择**：工作台信息架构采用客户确认的组合方案——以 A「任务指挥台」为主，保留 B 的「生命周期吞吐」板块和 C 的「当前上下文」板块。设计来源为客户高保真录入原型 `prototype/relocation-workbench/selected/relocation-workbench-selected.html`（该原型是设计依据，不是生产代码，后续将更新，对应行为契约见 workbench-interface 规格）。主要区域为：顶部 KPI/任务入口（月度运营指标与待办快速处理入口）、紧凑六阶段生命周期吞吐板块、高密度主项目队列、随选中项目/待办/阶段联动的常驻当前上下文侧栏、以及六个按需展开的详情 tab（项目总览、搬迁仪器、搬迁批次、上门活动、费用与掉票、申请与维修）。交互联动：点击项目行选中并刷新当前上下文与详情；点击待办联动选中其所属项目并定位到详情；点击生命周期阶段筛选项目队列并选中该阶段内项目；详情 tab 在选中项目内按需切换。本板块消费各领域模块既有事实与推导结果（D4），自身不维护业务状态，作为表现层模块纳入 D2 的逻辑接缝。

**理由**：待办快速处理与高密度项目队列构成主操作流，使负责人先处理逾期/临期待办再连续处理项目，是高密度连续操作的最优路径；生命周期吞吐以紧凑阶段带补充全局节奏与瓶颈判断，不重复建立看板；当前上下文在选中项目时集中提供状态异常、下一步待办、金额闭环与非阻塞事项，减少切换开销；详情 tab 按需展开避免主工作区信息过载。该组合是客户已确认的界面决策，不属于 25 项 TBD 暂定范围，本设计不得改变其结构或擅自视觉重构；数据录入方式与视觉可用性基线分别见 D15 与 D16，具体组件实现与像素级细节由 apply 阶段决定。

**被拒替代**：
- 以纯看板（B 项目流水线）为主界面：流动可视化虽直观，但降低高密度项目表的信息密度与连续操作效率，故仅以紧凑吞吐板块保留其全局节奏价值；
- 以纯单项目主从（C 主从工作区）为主界面：围绕单个项目深度处理会弱化待办与项目队列的全局主操作流，故仅保留其当前上下文板块；
- 把选定原型代码直接提升为生产实现：高保真录入原型是评审与交互验证用的自包含 HTML，生产实现必须重写但遵循其行为、结构与视觉意图，不复制其技术代码，也不把原型渲染结果作为生产交付物。

### D15 分层录入架构：新建向导 + 快速记录 + 就近入口

**选择**：数据录入采用分层入口，避免单个超大表单。全局「新建搬迁项目」采用四步向导（基本信息 → 搬迁范围 → 执行准备 → 确认方式），把项目级初始信息分步呈现；确认方式步骤展示录入摘要并支持保存为待进单、正式进单、未进单先执行三个确认路径，执行准备阶段允许留空后补的字段仅在满足 workbench-todos 既有七类逐类规则时生成对应标准待办，不承诺任意向导空字段都生成待办；向导录入单号时自动创建对应开单记录（工程师必填、生成日期默认当前日期、备注可空）。当前选中项目通过「快速记录」抽屉（Drawer）按业务动作分别打开搬迁批次、搬迁仪器、上门活动、开单记录、实际物流费用、验收报告、掉票、Ship-to 申请、损坏/维修事项、补齐进单核心资料等表单（二维码申请与序列号地址更新为独立模块，不进快速记录）；高优先项目队列行「记录」、当前上下文、详情 tab 标题栏均提供就近入口；点击待办先选中所属项目、再打开与待办类型匹配的表单。表单层只定义入口、字段呈现、校验反馈与提交后的展示同步；业务状态与金额校验等规则仍归对应业务能力，经 D4 推导入口消费（如掉票超额校验归属 project-financial-closure，interface 仅做即时提示与就地反馈），interface 不重复业务规则。

**理由**：负责人日常动作是"先待办、再按项目连续记录事实"，分层录入使每次录入只面对该动作所需字段，降低认知负担与出错率；就近入口让录入点贴近阅读位置，待办直达把"发现缺什么"与"在哪里补"直接连通；四步向导避免项目级初始信息的长表单，三个确认路径把进单方式在保存前显式收口。

**被拒替代**：
- 单一巨型通用表单承担全部录入：字段过多、必填/可后补混杂，认知负担高且难以按动作校验；
- 所有录入必须进入固定入口（仅全局新建或仅详情表单）：增加操作路径，不符合"待办直达、就近录入"的连续操作流；
- 在 interface 内重复实现业务状态与金额校验：与 D4/D8 所有权冲突，导致口径分叉、双份实现。

### D16 视觉与可用性基线

**选择**：工作台采用专业、克制、高密度的企业运营视觉风格（客户已确认，非 TBD）：正文默认字号不小于 14px、表格正文不小于 14px、辅助文字原则上不小于 12px（低于 12px 仅限纯装饰性角标并保持清晰可辨）；标题、正文、辅助文字与状态色具备清晰层级与足够对比，多行文本以可读行高呈现；表单控件提供必填/可后补标识、字段帮助、校验失败就地提示、禁用/提交中状态、成功 Toast 与空状态；Modal/Drawer/Toast 支持打开时焦点移至首字段、Escape 关闭、label 关联可访问名称、仅点击遮罩空白处关闭；1024px 桌面视口下不发生页面级横向溢出（必要宽表格在自身区域内内部滚动），1440px 为主布局基准。本决策只定可验收的可用性与视觉基线，不规定具体框架、组件库或像素级实现；高保真原型 `prototype/relocation-workbench/selected/relocation-workbench-selected.html` 提供行为与视觉意图，生产实现必须重写但符合该意图，不复制原型技术代码。

**理由**：客户明确要求提升录入方式、字体可读性、视觉层级、表单与整体美化质量；明确字号、层级与表单反馈基线使首版界面可验收、可测试，避免"好看但不可测"；1024/1440 视口约束保证高密度工作台在常见办公桌面下仍可操作；表单反馈与键盘可达性支撑负责人高频连续录入。

**被拒替代**：不设可验收的视觉基线、完全交由 apply 阶段临场决定（客户已确认方向，不应重新开放）；逐像素复制原型标记/样式/脚本作为生产代码（原型不是生产实现）；引入第三方 UI 框架或设计系统（属技术栈决策，留给 apply 前决策，不在本 change 选定）。

### D17 本地 SQLite 持久化

**选择**：应用作为 Windows 桌面应用（Electron + React + TypeScript）运行，全部业务数据持久化在应用本机的 SQLite 数据库中；数据库位于本地数据目录（具体目录、访问库与迁移工具按 apply 前决策，见 Open Questions）。领域层以 D1 稳定内部 ID、D4 事实记录与状态推导为存储模型，不依赖远程数据库或云服务；关闭并重新打开应用后数据保留。数据结构升级通过 schema 迁移执行，迁移失败时保留可恢复状态、不静默丢弃或损坏现有数据。本决策基于已确认的运行与持久化边界（TBD-16 已解决，ADR docs/adr/0001-windows-desktop-local-sqlite.md），对应 local-data-persistence 能力。

**理由**：仅个人使用的单机边界下，本地 SQLite 提供事务性、可备份的单文件持久化，运维与备份最简单，不引入网络依赖；事实 + 推导机制以关系型存储最直接；关闭重开保留与迁移保护保证数据连续性。

**被拒替代**：远程数据库/云数据库（与已确认边界冲突，增加运维与网络依赖）；服务端进程或外部服务（超出单机桌面边界）；内存或文件快照持久化（无法保证事务性与一致性）；数据库加密与应用密码（超出已确认边界，见 Non-Goals）。

### D18 本地备份：每日自动 7 份 + 手动备份/恢复

**选择**：应用在每日首次使用时，若当天尚无自动备份，则创建一份自动备份；自动备份仅保留最近 7 份，更旧的自动备份被清理，手动备份不受该数量限制。负责人可随时将数据手动备份到所选本地目录；可从所选本地备份恢复，恢复前要求确认并验证备份可读，恢复失败不得覆盖当前数据；备份或恢复失败时给出明确错误、不静默视为成功。备份内容为本地 SQLite 数据及其必要附属数据的可恢复副本（具体格式、文件命名与位置按 apply 前决策，见 Open Questions）。

**理由**：单机数据的保护依赖本地备份；每日自动备份 + 最近 7 份轮转在恢复窗口与磁盘占用间取得平衡；手动备份覆盖立即与重大变更场景；恢复前验证与失败保护避免"恢复即破坏"；明确失败反馈支撑负责人及时处置。

**被拒替代**：云备份/云同步（与已确认边界冲突）；只备份不做恢复验证（恢复路径不可信）；无轮转无限保留（磁盘占用不可控）；仅靠系统文件拷贝无版本化（无法满足最近 7 份轮转与恢复确认要求）。

## Risks / Trade-offs

- **R1（本地数据风险）本机敏感数据与单点故障**：业务数据仅存于单台 Windows 机器的本机 SQLite，存在本地敏感数据暴露、文件损坏、备份失效与安装升级影响数据的风险。→ 访问依赖 Windows 操作系统账户（D12）；每日自动备份仅保留最近 7 份 + 手动备份（D18）；备份/恢复失败明确报错且恢复失败不覆盖当前数据；恢复操作前可做安全快照（见 Open Questions）；Windows 安装包与升级流程纳入交付文档与验收。
- **R2 手工数据质量**：全部外部事实（经理批复、工程师执行、合同金额、区域等）由负责人手工录入，存在录入错误与口径漂移；区域为手工文本 trim 后精确分组（TBD-12），文本变体可能静默拆分分组。→ 在业务允许处做低成本校验（金额有值必须 > 0、必填原因、业务键唯一），按业务规则以警告而非阻断呈现；区域统一 trim 与单一维护点，报表下钻可查看组内明细以暴露分组异常。
- **R3 历史数据无法拆分或必填缺失**：一个合同对应多条执行记录等源数据无法明确拆分映射，或目标必填字段（含物流费用登记日期）缺失。→ 保留未分批并进入冲突清单由负责人确认，不按文本推断；dry-run 对目标必填缺失输出源文件/sheet/行/字段，客户修改源 Excel/补录模板后重跑，正式导入前不得存在错误、批次内任一目标必填字段缺失/错误则整个批次不写入且不产生部分导入；目标可选字段（含可选源业务时间）允许为空、不用导入时间替代；状态重建由事实确定性推导，不产生猜测状态。
- **R4 实时报表的一致性/性能**：报表对事实全量实时计算；事后编辑会改变历史统计——该变化由已确认规则（掉票直接覆盖编辑、取消排除收入/掉票指标，TBD-10 已解决）与暂定规则（TBD-12 区域使用手工文本且修改后历史报表实时重算、TBD-17 实时计算不建快照）共同导致，而非缺陷——但查询成本随数据量增长，且无法复现“某一历史时点”的报表快照。→ 单负责人、项目级聚合计算的量级下可行；如规模增长，索引/缓存优化属 apply 前决策；报表快照为 TBD-17 暂定 Non-goal，不复现历史时点属已接受取舍。
- **R5 直接编辑掉票缺乏历史版本**：proposal 已确认掉票“直接覆盖、不保留旧值，只记最后修改时间”，无法审计旧值。→ 按确认规则实现撤销（记录时间与原因）而非删除，并保留最后修改时间；将“无历史版本”作为已接受业务取舍在评审中向业务方明示；若后续要求版本化，将作为新 spec 变更而非本设计内补丁。
- **R6 暂定决定后续被推翻导致返工**：20 项未决暂定决定任意一项可能被修订。→ 决定集中登记于 proposal（D13）；按模块复核；D2 逻辑接缝与 D4 单一推导入口使规则修订局部化，不推倒整体架构。
- **R7 模块化单体边界的可调整成本**：边界是逻辑接缝，apply 阶段按实现便利调整会带来改动成本。→ 以稳定内部 ID 与领域内核降低模块耦合；调整限于模块内部实现，对 spec 定义的外部行为无影响。

## Migration Plan

存量数据一次性导入（对应 historical-data-import 能力），阶段流程与 D11 一致：

1. **冻结字段映射**：版本化记录源 Excel 列 → 目标模型字段的映射；多来源字段标注来源优先级（合同信息表 → 合同字段、项目执行表 → 执行字段、工作量统计表 → 开单/掉票动作记录）；评审确认后冻结，作为 dry-run 的输入。
2. **dry-run**：只读执行导入例程，产出解析报告（记录数、可映射/不可映射）、冲突报告（重复服务单号、多源冲突、无法拆分）与目标必填字段缺失错误清单（含源文件、sheet、行与字段）；不写任何数据；dry-run 检出目标必填缺失错误时由客户修改源 Excel 或补录模板后重跑；正式导入前不得存在错误，批次内任一目标必填字段缺失/错误则整个批次不写入、不产生部分导入。
3. **冲突人工确认**：负责人按冲突报告逐项确认（覆盖方向、保留未分批、手动指定等）；系统不自动覆盖、不推断。
4. **事务导入**：正式导入在 dry-run 无任何错误的前提下执行；每个导入批次作为一个整体提交或整体回滚，批次内任一记录失败则整体回滚、不产生任何部分数据；以“（源文件、sheet、行号）+ 业务键”为幂等键，已成功批次同源修复后重跑不重复写入；正式事务导入，导入后不存在待补必填字段，不建补录 UI；写入迁移审计记录（批次、时间、执行人员，执行人员为工作台外部署运维人员）。
5. **对账**：对比导入后的记录数、金额合计、掉票累计、状态重建结果与源文件。
6. **切换**：日常操作与报表切换到新模型，源 Excel 降级为只读参考，不再作为数据维护入口。

**时间口径（关键约束）**：导入/系统记录时间只作为审计时间保存；源业务时间（掉票时间、开单生成日期、实际物流费用登记时间、进单确认时间等）一律映射到对应业务字段；目标必填的源业务时间缺失由 dry-run 报错且该行不导入，目标可选的源业务时间缺失则保留为空、**绝不**用导入时间填充（TBD-18 已解决、验收场景 23）。项目状态不手工指定，由导入的事实经 D4 同一推导函数确定性重建。

**回滚**：dry-run 不写数据、天然可弃；事务导入按批次保证整体性，失败批次整体回滚、不产生部分数据；dry-run 检出目标必填缺失错误时由客户修改源 Excel/补录模板后重跑，正式导入前不得存在错误、批次内任一目标必填字段缺失/错误则整个批次不写入，不建补录 UI；执行前对源文件做只读副本备份。

**部署说明**：迁移作为一次性动作由**工作台外部的部署运维人员**执行，不新增管理员账号/角色、不进入工作台登录体系（无应用内登录，见 D12）；执行载体（CLI 或管理页）属 apply 前决策（见 Open Questions）。
