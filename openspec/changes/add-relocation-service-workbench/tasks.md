# 搬迁服务工作台 · 实施任务

本文件按依赖顺序拆分实施任务，属规划工件，不包含代码实现。实施基准为 docs/搬迁服务工作台.md v0.2（客户已确认）、proposal.md（已确认范围与 20 项未决暂定决定，TBD-07/10/11/16/18 已解决、当前高风险未决 0）、design.md（D1~D18 逻辑设计）与 14 份能力规格（specs/*/spec.md）。工作台信息架构与数据录入以客户确认的高保真录入原型（prototype/relocation-workbench/selected/relocation-workbench-selected.html）为设计依据，其行为、结构与视觉意图由 workbench-interface 规格定义（见第 9 组）；原型不是生产实现，视觉与可用性基线（字号、层级、表单反馈、1024/1440 适配）按 workbench-interface 规格执行，具体组件实现细节由 apply 阶段决定，本文件不预设。运行与持久化架构已确认（Windows 桌面、Electron + React + TypeScript、本地 SQLite、无应用内登录、自动/手动备份恢复，见 ADR docs/adr/0001-windows-desktop-local-sqlite.md 与 design D12/D17/D18）。

约定：模块所有权为 relocation-project-lifecycle 唯一拥有主状态推导入口（design D4），workbench-todos 与 operational-reporting 只消费事实、不拥有业务状态（D9/D10），operational-reporting 唯一拥有统计公式，workbench-interface 为表现层、只消费事实与推导结果、只定义录入入口与反馈、不重复业务状态与金额校验规则（D14~D16），local-data-persistence 拥有本地数据存储、备份与恢复（D17/D18）。验证顺序为领域层场景测试优先、UI 层冒烟验收在后（见 10.4），每个任务以"完成态"给出可验证验收标准。技术栈已确认（Electron + React + TypeScript + 本地 SQLite，见 ADR 与 D12/D17/D18），具体版本、打包器、SQLite 访问/迁移库与数据目录按 0.2 决策确定，本文件不预设具体库或命令。已解决 TBD-07/10/11/16/18 不再作为评审门；剩余 20 项中/低风险暂定决定按所属模块在对应能力实现前复核确认（design D13），本文件对应任务已标注复核归属；本文件最终任务（10.7/10.8）要求运行 openspec validate 与等效验证流程，但仅在 apply 阶段执行。

## 1. 项目与领域基础

- [ ] 1.1 建立工程骨架：按已确认技术栈（Electron + React + TypeScript）建立 Windows 桌面应用项目结构，模块划分与 14 个 capability 一一对应，配置统一入口；完成态：骨架可启动/可编译，测试入口可执行并通过空测试，模块清单与 design D2 模块接缝一致。
- [ ] 1.2 实现稳定内部 ID 与业务 ID 分离的基础设施：内部 ID 创建时生成、全局唯一、不复用，作为全部引用与关联的键；ECC、服务单号、Account ID、仪器序列号、客户外部编号等业务 ID 作为独立字段保存并各自具备可空与唯一性约束；完成态：领域层提供内部 ID 分配与业务 ID 唯一性校验能力，配套领域测试通过，覆盖 design D1。
- [ ] 1.3 实现金额值对象：十进制定点、两位小数、四舍五入，可表达 0 与负差异，支持相加/比较/占比等币种运算；物流费用按人民币口径；备件金额仅 USD/RMB，RMB 按固定常量 1 USD = 7.2 RMB 折算为 USD；值对象本身不施加正数约束，"用户录入金额有值必须大于 0（不得为 0 或负数，无 0 金额闭环）"由各录入/领域校验在对应能力内落实；完成态：金额精度（含 1234.567→1234.57 用例）、舍入、零/负差异表达与折算的领域测试通过，全程不涉及二进制浮点，覆盖 design D7。
- [ ] 1.4 建立领域测试基础设施：领域层测试框架、事实集合构造工具与状态推导断言辅助；完成态：示例领域测试可运行并通过，事实集合构造可覆盖各能力 spec 场景。
- [ ] 1.5 实现业务时间与审计时间分离及事实来源标记：业务事件作为事实记录持久化，携带来源标记（负责人手工录入/系统自动记录/迁移导入）与独立审计时间；完成态：事实记录结构与来源标记的领域测试通过，为 design D4/D11 及 workbench-access"迁移数据不计手工录入"提供基础。
- [ ] 1.6 实现客户主数据：客户以内部 ID 标识，外部编号可空但唯一，名称可不唯一，一个客户可关联多个合同、搬迁项目、Ship-to 与申请；完成态：relocation-project-lifecycle「客户识别与关联」中客户侧规则的领域测试通过（项目侧关联规则见 2.1）。
- [ ] 1.7 实现合同草稿与项目基础模型：合同与项目 1:1 独立建模（合同持有临时编号、ECC 字段、合同 USD 含税金额、进单金额快照与最终可确认金额字段占位、正式合同变更记录占位），项目持有进单时间（待进单可空、正式进单必填默认当前可补录）、区域、旧址/新址联系人、项目默认旧址/新址、合同起止日期（截止不得早于开始，校验在 2.6 落实）、未进单先执行标签、取消信息、客户关联；不设项目负责人字段；完成态：待进单时同步建立不完整合同草稿并分配稳定内部 ID 与系统临时编号的领域测试通过（正式进单补 ECC 等完整行为见 2.1，金额行为见 5.1~5.4）。
- [ ] 1.8 实现集中状态推导入口骨架：状态枚举（待进单、待执行、执行中、待验收、待掉票、已完成、已取消）齐全，推导函数以"事实集合→主状态"形式组织并由 relocation-project-lifecycle 模块唯一拥有；完成态：空事实推导为待进单的领域测试通过，代码结构与测试强制"lifecycle 拥有状态推导、todos/reporting 只消费"的所有权约束（design D4/D9/D10）。
- [ ] 1.9 实现本地 SQLite 数据层与 schema：按 0.2 确定的数据目录与访问库初始化本机 SQLite，schema 覆盖 14 个能力的事实与主数据模型；领域事实全部落库，关闭并重开应用后数据保留；完成态：local-data-persistence「本机 SQLite 持久化」场景测试通过（含关闭重开保留用例），数据层与 design D1/D4 存储模型一致。
- [ ] 1.10 实现 schema 迁移机制：数据结构升级时迁移现有本地数据，迁移失败保留可恢复状态、不静默丢弃或损坏现有数据；完成态：local-data-persistence「schema 升级迁移本地数据」场景测试通过（含注入失败保留可恢复状态用例）。
- [ ] 1.11 实现每日自动备份与最近 7 份轮转：每日首次使用且当天尚无自动备份时创建备份；自动备份仅保留最近 7 份、清理更旧自动备份，手动备份不受数量限制；完成态：local-data-persistence「每日自动备份」「自动备份仅保留最近 7 份」场景测试通过。
- [ ] 1.12 实现手动备份与恢复及失败保护：负责人可立即备份到所选本地目录；可从所选本地备份恢复，恢复前确认并验证备份可读，恢复失败不覆盖当前数据；备份/恢复失败给出明确错误、不静默成功；完成态：local-data-persistence「立即手动备份」「从本地备份恢复」「备份/恢复失败明确反馈」场景测试通过。
- [ ] 1.13 验证 local-data-persistence 能力：将 spec 全部场景转为可执行测试并全部通过（含离线启动、关闭重开、自动备份轮转、手动恢复失败保护）；完成态：场景测试全绿。

## 2. 访问与核心生命周期

- [ ] 2.1 实现正式进单：校验合同、客户单位、搬迁范围齐备，任一缺失拒绝进单并生成"缺进单核心资料"待办信号（待办派生见 6.2）；进单时间在正式进单时必填，默认取当前时间、允许补录或修正、待进单阶段可空；补充唯一 ECC，缺 ECC 拒绝进单，ECC 全局唯一，进单后纠错通过唯一性校验并自动记录最后修改时间；保存进单金额快照（快照规则见 5.2）；不记录销售通知时间、不设项目负责人字段；完成态：relocation-project-lifecycle「正式进单」「合同草稿、内部编号与 ECC」全部场景领域测试通过（本项实现前复核 TBD-01/25 归属规则）。
- [ ] 2.2 实现主状态推导规则与未进单先执行：主状态由业务事实推导、禁止直接编辑；首次上门活动开始或首个搬迁批次开始运输→执行中（仅完成排期、工程师或运输公司安排不计）；正式进单→待执行；带"未进单先执行"标签时主状态保持待进单，进单后按已发生事实跳到待执行/执行中/待验收且在原项目上进单、不新建项目；完成态：「主状态与标签」「主状态由事实推导」「未进单先执行」全部场景领域测试通过（其中跳转待验收依赖 2.3 的实际装机完成时间事实，本项实现前复核 TBD-08/09 归属规则）。

- [ ] 2.4 实现项目验收：标记已有验收报告并填写报告形成日期→待掉票，不以客户确认为前置条件；完成态：「项目验收」场景领域测试通过。
- [ ] 2.5 实现取消：任一未取消主状态且无任何掉票历史（含已撤销）的项目可取消，取消必须记录取消时间与原因并保留已发生的上门活动、物流与费用记录；存在任何掉票历史（含已撤销掉票）的项目禁止取消；已取消项目不可恢复；已取消期间禁止修改合同金额、最终可确认金额与掉票记录；完成态：「取消」全部场景领域测试通过（取消期间金额/掉票冻结在 5.11 联动验证，统计排除口径见 7.9，TBD-10 已解决）。
