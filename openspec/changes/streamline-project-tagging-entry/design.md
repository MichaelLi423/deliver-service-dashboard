## Context

See `proposal.md` - Why。本变更只调整 renderer 中项目标签分配的入口、弹窗和命名，不改变标签库、项目标签关联或 IPC 契约。

当前项目队列行与项目详情已从 `WorkbenchProjectRow.groupedTags` / `WorkbenchV2ProjectDetailDto.groupedTags` 展示分组标签，完整“编辑项目资料”也已复用 `GroupedTagPicker` 编辑 `tagIds`。保存经 `v2Mutate({ op: "update_project", payload: { projectId, tagIds } })` 进入现有事务；主进程支持仅提交 `tagIds` 的独立更新，并返回 `projects`、`project:<id>` 等失效范围。renderer 的 `mutate` / `refreshInvalidated` 已按失效范围重读当前队列页，并在目标为当前选中项目时重读当前项目详情，用业务修订号拒绝过期响应。

现有通用 `Layer` 提供模态语义、初始聚焦、焦点圈定、Esc/遮罩/关闭按钮关闭、返回触发点及脏状态放弃确认。视觉上已有标签蓝灰色、品牌深绿、边框、圆角、按钮和错误/成功反馈样式；新交互应复用这些语言，不另建视觉体系。队列是固定每页 20 项的高密度横向可滚动表格；窄窗口下工作区会改为单列，顶部导航和详情页签允许横向滚动。

## Goals / Non-Goals

**Goals:**

- 让详情中的标签展示和空标签状态始终占据同一稳定位置，并在其旁提供可预期的项目级主入口。
- 让队列每行可直接为该行项目打开同一编辑器，不依赖先切换工作区、滚动到详情或进入完整资料表单。
- 让共享编辑器只形成 `{ projectId, tagIds }` 更新，且保存、关闭、失败和并发刷新行为可明确实现与测试。
- 在宽、窄窗口中保持入口可见、弹窗可操作、键盘与屏幕阅读器语义完整，并延续当前产品视觉语言。

**Non-Goals:**

- 不新增后端命令、preload/IPC 字段、数据库表、迁移或标签数据模型。
- 不重构完整“编辑项目资料”与新建项目中已有的标签选择；它们继续复用同一 `GroupedTagPicker`，本变更仅新增轻量项目标签编辑容器。
- 不提供批量打标签：批量选择、部分选中态、失败回滚和权限/确认语义会把单项目就近维护扩大为新的工作流。
- 不提供右键菜单：入口不可见、键盘与触屏可发现性差，也会与表格当前点击/键盘选行模型冲突。
- 不把标签混入“快速记录”：标签是项目分类关联，不是业务事实记录；混入会模糊语义，并增加一次无关动作选择。
- 不在表格内展开全部标签：标签数量不定，会破坏固定行高与快速扫读，增加横向宽度并放大重排成本。

## Decisions

### 1. 以项目 ID 驱动独立的共享标签编辑层

在 `LayerState` 增加携带 `projectId` 与来源（详情或队列）的项目标签编辑状态，而不是只依赖全局 `selectedId`。两个入口均渲染同一个轻量 `ProjectTagEditForm`（名称可按实现惯例调整），由该组件复用 `GroupedTagPicker`。

- 详情入口传当前详情项目 ID。
- 队列入口传被点击行的项目 ID、行 DTO 的 `tagIds` 及目标展示信息；阻止行点击冒泡，且不改变当前 `selectedId`、工作区或项目详情。弹窗数据和提交目标均以 layer 内固化的行项目数据及 `projectId` 为准，避免可变选中状态把保存落到错误项目。
- 弹窗标题固定为“编辑项目标签”，副标题显示客户名称及 ECC/临时编号，帮助用户在连续处理队列时核对目标。

打开时以目标项目当前可用的 `tagIds` 建立本地草稿：详情入口使用当前详情 DTO，队列入口使用 layer 固化的行 DTO。由于队列页和详情 DTO 已带 `tagIds`，正常打开不增加读取请求。标签目录仍使用顶层已缓存的 `tagCatalog`；目录尚在加载或加载失败时沿用 `GroupedTagPicker` 的加载、错误和重试状态。

选择此方案是为了把“编辑哪个项目”与当前选中状态解耦，同时保留现有单层 `Layer` 架构和目录缓存。替代方案是从队列入口先选中、等待详情读取完成后再打开完整“编辑项目资料”；该方案会改变当前工作区、延迟更高，可能出现选中竞争，也违背轻量入口目标。另一替代是调用 `v2TagCatalog(projectId)` 重新读取选中项；现有项目 DTO 已具备所需数据，额外请求没有收益，并扩大失败面。

### 2. 详情标签区始终渲染，并把编辑动作放在标签旁

把详情中目前可能返回 `null` 的纯 `GroupedTags` 展示改为稳定的标签区容器：区头为“项目标签”，右侧提供“编辑标签”按钮；有标签时继续按现有分组与标签样式展示，无标签时在同一内容位置显示克制的空状态“尚未添加项目标签”，并将动作文案呈现为“添加标签”。按钮的无障碍名称包含当前项目，且仅在有项目时可用。

宽窗口下区头与操作同行，标签内容在下方换行；窄窗口下区头可换为上下排列，但按钮保持完整文字和至少现有 40px 操作高度，不退化为仅图标。空状态不使用占据大面积的通用 `Empty` 插画式区块，以免在详情顶部制造过强视觉重量。

选择标签旁的常驻动作，而不是只在详情页头或“编辑项目资料”按钮组中追加入口，是因为其对象与结果在空间上直接相邻，空状态也能保留相同入口位置。替代方案是让标签胶囊本身可点击；这会让展示元素的可交互性不清晰，并难以提供明确焦点样式。

### 3. 队列“就近录入”单元格并列“标签”快捷动作

保留现有“就近录入”列，在每行同一操作单元格内并列“记录”和“标签”两个文字按钮。点击“标签”时阻止行点击冒泡，以该行固化的项目数据打开共享编辑弹窗，不改变当前 `selectedId`、工作区或项目详情。无标签项目仍显示同一“标签”动作，不因状态变化造成列内布局跳动；可用 `aria-label="编辑〈客户〉的项目标签"` 明确动作和目标。

宽窗口下两个动作横向排列；窄窗口不把标签展开进表格，而是允许该操作单元格中的动作紧凑换行或纵向排列，表格继续使用现有横向滚动。两项动作均保持可见文字、焦点环和足够点击高度。按钮获得焦点时，现有行级键盘处理因事件目标不是行本身而不抢占按键；关闭弹窗后焦点返回实际触发按钮。

选择复用单一操作列可避免再增加一列和表格最小宽度。替代方案是在客户单元格的紧凑标签展示上附加编辑按钮；该区域信息已密集，且空标签行没有稳定锚点。也不使用省略号菜单，因为两项高频动作值得直接暴露。

### 4. 弹窗采用“固定头尾 + 中部内部滚动”的轻量结构

共享编辑器继续使用通用 `Layer` 的居中 modal 形态，不使用宽抽屉。弹窗宽度以能舒适容纳 `GroupedTagPicker` 的双列分组为上限；窄窗口下接近视口宽度并将选择器切为单列。弹窗整体受 `100dvh` 约束：标题区固定，中间选择区 `overflow-y: auto`、`overscroll-behavior: contain`，底部操作区固定并由边框/浅色背景与内容区分。这样标签库较长时只滚动弹窗内部，标题、错误反馈和保存/取消操作不会滚出视口。

底部提供次要“取消”和主要“保存标签”按钮，并显示“已选择 N 个标签”；空选择是合法草稿，保存表示清空项目标签。目录为空时显示“标签库暂无内容”，提供“管理标签库”的文字指引但不在当前模态上叠加第二层标签库弹窗；用户可取消后从顶部进入标签库。目录加载或读取失败时禁用保存，避免把“目录未知”误提交为清空。

选择居中轻量弹窗是因为任务短、上下文单一，并可直接复用现有 Layer 的可访问行为。替代方案是侧边抽屉；其视觉权重接近完整资料编辑，也会在窄窗口占满并削弱“轻量”感。表格内 popover 在标签较多、需要滚动和错误反馈时空间不足，且更难可靠圈定焦点。

### 5. 精确脏状态、关闭语义与提交状态

本地草稿按标签目录顺序规范化后与打开时的有效 `tagIds` 比较；顺序不影响是否脏。只有集合发生变化才视为脏，切换后再恢复原集合会回到未修改状态。保存按钮在未修改、目录不可用或提交中禁用；未修改时无需发送空更新。

- 打开后焦点进入选择器中的首个可用复选框；若无可选标签，则进入“取消”或重试按钮。Tab/Shift+Tab 由 `Layer` 圈定在弹窗内。
- 未修改时，Esc、关闭按钮、遮罩点击和“取消”直接关闭；已修改时均进入现有“放弃本次修改？”确认。确认层上的 Esc 只关闭确认并回到原弹窗，继续编辑后焦点回到触发关闭的控件。
- “取消”与关闭图标语义一致，不保存。提交中禁用选择、取消、关闭和重复提交；Esc/遮罩不关闭，避免用户误以为已取消正在进行的写入。
- 关闭成功后由 Layer 把焦点还给详情或对应行的标签按钮。若队列刷新后触发按钮已卸载，则允许自然落回文档，不主动跳到无关项目。

通用 `Layer` 目前通过任意 input/change 事件把 ref 永久置脏，无法识别“改回原值”，且未直接暴露提交锁定。因此实现时应让共享编辑器向 Layer 提供受控的 `dirty` / `busy` 状态，或提供等价的局部关闭守卫；优先小幅扩展 Layer，同时保持现有表单的默认事件捕获行为不变。替代方案是沿用永久脏标记，代码更少但会在已恢复原值时仍阻挡关闭，不符合本交互的精确性要求。

### 6. 仅提交 `update_project` 的 `tagIds`，成功后按失效范围同步全部可见副本

保存请求固定为：

```ts
updateProjectRequest({ projectId, tagIds: normalizedTagIds })
```

不得混入客户、区域、状态或详情字段。`normalizedTagIds` 由 `validCatalogTagIds` 按当前目录顺序过滤和去重，空数组表示明确清空。继续使用 `mutate` 接收业务修订号并调用 `refreshInvalidated`，不直接拼接或乐观修改 `groupedTags`。

成功路径等待失效读取完成后再关闭弹窗并显示现有成功 toast。`projects` 重读更新当前队列页的紧凑标签；仅当目标恰好是当前选中项目时，才通过 `project:<id>` 重读同步当前上下文和详情标签区。队列入口编辑非当前项目时保持现有工作区与详情不变；完整“编辑项目资料”随后打开时从刷新后的对应 detail/row 取得最新 `tagIds`。业务修订号继续防止旧响应覆盖新结果。

写入失败时弹窗保持打开、保留草稿和脏状态，在选择器与底部操作之间显示 `role="alert"` 的具体错误，并恢复可编辑/可重试；不得显示成功 toast或局部伪造已保存标签。若写入已经成功但后续失效读取失败，现有 `mutate` 会把整体 Promise 视为失败，可能诱发重复提交。实现时需区分“写入失败”和“写入成功后刷新失败”：后者关闭弹窗、显示“标签已保存，部分视图刷新失败”的警告，并触发/提供重读，不鼓励再次写入。可通过让刷新返回可识别结果或在该专用保存路径中分阶段处理达成，不改变 IPC。

选择服务端结果驱动的重新读取而不是乐观同步，是因为同一标签在队列、上下文、详情和完整编辑器有多个副本，规范分组顺序也由目录/读取模型决定。替代方案是在 React 状态中逐处替换 `tagIds/groupedTags`，即时感更强，但容易遗漏副本并与业务修订竞争。

### 7. 顶部标签库命名明确区分“维护目录”与“分配项目”

顶部主导航的“标签管理”改为“标签库”，其打开的全局维护层标题/主要动作语义统一为“管理标签库”；数据管理菜单中的“项目分类标签库”可统一显示为“管理标签库”。标签库面板内部继续说明“所有项目共用”，不改其创建分组与标签能力。项目详情和队列只使用“编辑标签/添加标签”，不使用“管理”，从文案上区分项目分配与全局目录维护。

选择短名称“标签库”作为导航项，可在窄窗口降低横向占用，并与“编辑项目标签”形成对象层级。替代方案是保留“标签管理”，但“管理”无法说明是在维护全局目录还是当前项目分配，正是本变更要消除的歧义。

### 8. 验证矩阵只以正式规格基线为来源

`npm run verify:matrix` 的 `build-verification-matrix.mjs` SHALL 扫描正式基线 `openspec/specs/`，不得硬编码某个 active 或 archived change 的 specs 路径，也不得自动合并 change delta。active change（包括本 change）的规格完整性继续由 `openspec validate <change> --strict` 验证；当 change 归档或同步进入正式基线后，其场景才自然成为矩阵输入。

场景登记表仍是正式基线场景到测试证据的唯一登记来源。脚本 SHALL 继续从测试标题字面量校验证据；测试标题演进导致的失效登记必须更新为当前真实标题。不得为本 change 尚未存在于正式基线的 13 个场景预先添加矩阵映射，以避免产生无法对应基线场景的孤儿登记。

选择此边界是为了让生成矩阵反映已发布规格，而非随工作中的 delta 改变；严格 OpenSpec 验证则保留对未归档规划制品的完整性检查。替代方案是扫描当前或所有 change delta，但会把未同步、已归档或并行变更混入正式覆盖口径，并要求为不存在于基线的场景维护登记。

### 9. 验证聚焦交互完整性和可实施边界

renderer 组件测试应覆盖：详情有/无标签时入口与空状态；队列行入口以行 DTO 的固定项目 ID 和 `tagIds` 打开编辑器、阻止冒泡且不改变当前选中项目/工作区/详情；两个入口共享标题和选择行为；只发送 `update_project` + `tagIds`；清空标签；无变化禁用保存；目录加载/空/失败；宽窄布局所依赖的稳定类与可见动作；初始焦点、焦点圈定和关闭后焦点恢复；Esc/取消/遮罩在干净、脏和提交中状态下的差异；弹窗内部滚动容器；保存后刷新队列，且仅在目标为当前选中项目时重读上下文和详情；写入失败保留草稿；写入成功但刷新失败不重复写入；顶部“标签库/管理标签库”命名。

既有 integration 测试已覆盖 tag-only `update_project` 的原子替换、清空、未知标签及已取消项目规则，因此本变更无需新建数据库或 IPC 测试，除非实现时改变现有契约（本设计禁止该改变）。

## Risks / Trade-offs

- [队列标签动作误触发行点击或依赖当前选中状态，可能改变工作区或保存到错误项目] → 阻止冒泡，layer 固化行 DTO 与 `projectId`，提交绝不从可变 `selectedId` 推导。
- [标签目录在弹窗打开期间变化，草稿包含已删除或未知 ID] → 提交前按最新目录过滤并使用现有服务端校验；目录刷新导致有效选择变化时明确保持脏状态，不静默宣称已保存。
- [标签数量增长使弹窗超过窗口] → 限制弹窗高度，只有中部选择区内部滚动，头尾始终可达；窄窗口改为单列。
- [共享 Layer 的现有事件式脏标记无法表达恢复原值或提交锁定] → 以向后兼容的受控状态扩展或局部守卫实现，现有表单仍沿用默认行为，并补回归测试。
- [成功写入后的刷新失败被误判为写入失败，用户重复提交] → 分离写入与刷新反馈；已确认写入成功时不保留“可再次保存”的错误态，改为警告并重读。
- [队列新增第二个直接动作增加视觉密度] → 复用现有文字动作样式和单一“就近录入”列，不新增图标、菜单或标签展开；窄窗口允许操作组换行。
- [完整“编辑项目资料”和轻量弹窗同时存在，用户可能困惑] → 详情标签旁把轻量入口设为标签主入口；完整资料编辑仍可修改标签以保持兼容，但文案不把它宣传为首选路径。
- [已取消项目的普通资料更新受限] → 继续使用后端已允许的 tag-only 更新；前端请求不得夹带其他字段。
- [验证矩阵随 active 或 archived change 路径漂移，导致基线验证被历史制品阻塞] → 扫描来源固定为 `openspec/specs/`，change delta 单独以 `openspec validate <change> --strict` 验证。
- [测试标题演进使已登记的正式基线场景被误报为缺证据] → 更新登记关键词为当前真实标题，并保持脚本对标题字面量的校验。

## Migration Plan

1. 在 renderer 内增加带固定项目 ID 的项目标签 layer 状态和共享轻量编辑组件，复用 `GroupedTagPicker`、目录缓存、`updateProjectRequest` 与失效刷新机制。
2. 将详情标签展示包装为稳定的有标签/空标签区域并接入主入口；在队列现有“就近录入”操作组接入同行快捷入口。
3. 补齐受控脏状态、提交锁定、内部滚动及宽/窄窗口样式；沿用现有颜色、字型、边框、圆角、焦点环和反馈组件。
4. 统一顶部与标签库层的“标签库/管理标签库”命名，并更新对应 renderer 测试。
