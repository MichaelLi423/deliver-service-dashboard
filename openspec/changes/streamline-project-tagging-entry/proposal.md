## Why

项目分类标签虽已支持独立更新，但当前必须从项目队列选中项目，再经项目总览和“编辑项目资料”中的多个分组才能完成分配；详情与队列中的既有标签展示点又均为只读。为让负责人能在查看项目或连续处理队列时就近维护分类，需补足稳定入口并明确标签库维护与项目标签分配的区别。

## What Changes

- 在项目详情的标签展示旁提供稳定的“编辑标签”主入口；空标签项目在同一位置提供添加入口。
- 在高密度项目队列既有就近录入列增加标签快捷入口。
- 两个入口共用轻量“编辑项目标签”弹窗，仅更新项目的 `tagIds` 独立关联。
- 统一轻量弹窗的关闭守卫：脏草稿先确认放弃，干净草稿直接关闭，提交中禁止关闭；保存按现有 replace-set 的 last-write-wins 语义处理。
- 将顶部“标签管理”调整为“标签库”，其管理操作调整为“管理标签库”，以区分全局标签库维护和项目标签分配。
- 将 `npm run verify:matrix` 的扫描来源固定为正式基线 `openspec/specs/`；active 或 archived change 的 delta 继续由各自的严格 OpenSpec 验证负责，归档/同步到正式规格后才自然进入矩阵。
- 移除验证矩阵脚本对旧 change 的硬编码，并将因测试标题演进失效的场景证据登记更新为当前真实标题，使正式基线矩阵可通过。
- 不纳入批量打标签、右键菜单、将标签混入快速记录，或在表格内展开全部标签。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `workbench-interface`: 为项目分类标签增加详情稳定编辑入口、队列表格快捷入口、空状态添加入口和共享编辑弹窗，并调整标签库维护入口的命名以区别项目分配。

## Impact

- 主要影响 renderer 中的项目详情、项目队列、标签库入口及其交互状态，相关样式与界面测试。
- 复用现有项目 `tagIds` 独立更新能力；不改变后端数据模型、IPC 契约或标签库数据结构。
- 影响验证矩阵脚本及其场景证据登记：矩阵只覆盖正式规格基线，规格路径解析兼容 Windows/macOS；不提前为本 change 的 ADDED Requirements 下尚未同步到正式基线的 17 个场景登记映射。
- 规划制品将为 `workbench-interface` 增补 OpenSpec delta，后续实现与测试范围以该规格和设计制品为准。
